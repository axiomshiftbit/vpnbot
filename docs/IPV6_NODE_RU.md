# Два VPN-бота: IPv6 между серверами и до сайтов

Схема: клиент → основной бот A → **IPv6** → узел B → **IPv6** → сайт.
Клиент может подключаться к A по IPv4. На A и B нужен работающий публичный IPv6.
Если у A только IPv4, он может подключаться к B по IPv4, а B — выходить к сайтам
через IPv6. Для IPv6 между A и B IPv6 необходим обоим серверам.

## Две независимые настройки

В B: **Xray → Узлы выхода → Принимать трафик других ботов → профиль**:

* **Связь с узлом: IPv6** — в ссылке и её подписке адрес B заменяется буквальным
  IPv6. SNI, ключи Reality и остальные параметры сохраняются. Поддерживается
  **Reality TCP/443**. Кнопка не изменяет firewall.
* **Выход: только IPv6** — трафик этого профиля выходит к сайтам исключительно
  по IPv6. Эта настройка работает и при подключении A → B по IPv4.

Обычный режим связи сохраняет прежний адрес из настроек бота. Остальные
пользователи B не переключаются. В режиме IPv6 недоступная сеть либо смена
Reality на другой транспорт не подменяют ссылку вариантом IPv4: ссылка перестаёт
выдаваться. На A при этом сохраняется последняя полученная ссылка.

## Подготовка хостов A и B

Сначала настройте IPv6 у провайдера и на хосте. Не отключайте IPv6 в GRUB,
netplan или sysctl. Для маршрутизации из Docker нужен
`net.ipv6.conf.all.forwarding=1`. Если маршрут приходит через RA, проверьте
`accept_ra=2` на WAN и заполните `ipv6_routers` доверенным link-local адресом
маршрутизатора. Не разрешайте RA от произвольных источников.

Проверьте адреса, маршрут и флаги, не выводя конфиги с ключами:

```sh
ip -6 address show scope global
ip -6 route show default
sysctl net.ipv6.conf.all.forwarding
```

Для установки используйте обновлённый профиль `nftables/nftables.conf` с интерфейсом своего сервера. Их IPv6-часть содержит
`egress6_snat`, `node6_sources`, `node6_public` и закрытые `input`/`forward`.
Профили только Relay и FR с иной сетевой схемой нельзя считать эквивалентной
заменой: сначала нужен профиль VPN-бота и его выделенная сеть.

В `/etc/nftables.conf` каждого сервера заполните `egress6_snat`:

```nft
map egress6_snat {
    type ipv6_addr : ipv6_addr
    elements = { fd42:7662:6::9 : ПУБЛИЧНЫЙ_IPV6_ЭТОГО_СЕРВЕРА }
}
```

Здесь и ниже слова-заглушки нужно заменить своими адресами. Это параметры
конкретного сервера; не публикуйте заполненные файлы в GitHub.

На B заполните входные наборы. На A оставьте их пустыми, если A не принимает
другие узлы по IPv6:

```nft
set node6_sources {
    type ipv6_addr
    elements = { ПУБЛИЧНЫЙ_IPV6_A }
}
set node6_public {
    type ipv6_addr
    elements = { ПУБЛИЧНЫЙ_IPV6_B }
}
```

Допускаются несколько отдельных доверенных адресов через запятую. Не добавляйте
целые сети или адреса пользователей. Для A указывайте адрес из его SNAT-карты.
Для B указывайте адрес, назначенный его WAN, совпадающий с адресом подготовки.
Оба набора по умолчанию пусты: вход остаётся закрытым.

После редактирования выполните штатную атомарную загрузку с резервной копией:

```sh
sudo nft -c -f /etc/nftables.conf
sudo systemctl restart nftables-after-docker.service
sudo systemctl status nftables-after-docker.service --no-pager
```

Эта команда предполагает установленную службу применения из комплекта `/opt`.
Не очищайте правила отдельной командой `nft flush ruleset`. Перед изменением
firewall сохраняйте действующий SSH-сеанс и доступ к консоли провайдера.

В каждом боте сначала добавьте **IPv6 этого сервера**, чтобы обычный выход
получил защиту от случайного перехода на IPv6. Затем на хосте:

```sh
cd /root/vpnbot
read -r -p 'Публичный IPv6 этого сервера: ' VPNBOT_PUBLIC6
read -r -p 'WAN-интерфейс: ' VPNBOT_WAN
sudo python3 scripts/ipv6_egress.py prepare \
  --public "$VPNBOT_PUBLIC6" --interface "$VPNBOT_WAN"
make r
```

Если каталог бота другой, измените `cd`. `prepare` проверяет адрес, маршрут,
forwarding, защиту обычного выхода и SNAT, записывает локальную настройку сети;
ключи клиентов он не выводит. `make r` — штатный запуск/пересоздание контейнеров,
возможен краткий перерыв. Если прежний setup выключил IPv6 через GRUB, сначала
исправьте настройки и перезагрузите хост в согласованное время.

## Назначение трафика

1. На B выберите Reality, создайте профиль узла и включите обе IPv6-настройки.
2. На A добавьте его ссылку в **Узлы выхода → Добавить выход → Удалённый сервер**.
3. В настройках узла добавьте подписку профиля B. Она обновляет ключи и IPv6
   автоматически; адрес скачивания подписки может оставаться обычным HTTPS
   по IPv4 — это не транспорт пользовательского трафика.
4. Добавьте `domain:youtube.com`, другие домены или наборы `.srs/.mrs`,
   `geosite:`, `geoip:`, `ext:`, `extip:`, IP/CIDR и назначьте пользователей.
5. Для полной строгой цепочки выберите на A **При отказе: блок**.
   **Прямой выход** разрешён отдельно и может вывести выбранный трафик через A,
   в том числе до первых успешных проверок после запуска.
6. Используйте **Диагностика → Проверить** и **Куда пойдёт домен**.

Для YouTube обычно нужны также домены доставки видео, например
`googlevideo.com` и `ytimg.com`; готовый актуальный набор проще сопровождать.
Правило выбирает маршрут, но не создаёт IPv6 у назначения. Доменам сайтов нужны
AAAA-записи. Буквальный IPv4, включая IPv4 из CIDR-правила, не преобразуется в
IPv6 и в строгом выходе блокируется. IPv4 CIDR сам по себе не сопоставляется
с IPv6-адресом того же сервиса. Для таких сервисов предпочтительны доменные правила.

## Сертификаты и окно SSL

Для исходящего соединения IPv6 отдельный сертификат не требуется. Reality
между ботами использует существующие параметры Reality. AAAA у имени самого
VPN-сервера для этой схемы не нужна: в ссылке указан IPv6, SNI сохранён.
Окно ACME продолжает работать по IPv4/80; его запрет неподготовленных AAAA
сохраняется. Не добавляйте AAAA к доменам бота только ради данной функции.

## Что защищает firewall

* Новые входящие IPv6-соединения закрыты, кроме TCP/443 после DNAT к Xray
  от адресов `node6_sources` на адреса `node6_public`.
* SSH, панели, DNS и внутренние API по IPv6 не открываются. Прямой пакет с WAN
  на ULA контейнера не заменяет обязательный DNAT.
* Новые SYN ограничены отдельно на источник: 50/с, всплеск до 100.
  Ключи Reality и UUID остаются обязательными; доверенный IP не заменяет их.
* Ответы, ICMPv6 для PMTU и NDP обрабатываются штатными правилами. Redirect
  блокируется, RA принимается только от явно заданного маршрутизатора.
* Origin guard связывает трафик контейнера с его veth, MAC и назначенными
  адресами; подмена только IP внутри Docker не даёт прав другого контейнера.
* Без SNAT ULA не выходит в WAN. IPv4-правила и окно ACME сохраняются.

Проверки:

```sh
sudo nft list set ip6 filter node6_sources
sudo nft list set ip6 filter node6_public
sudo nft list chain ip6 filter node6_ingress
sudo systemctl status vpnbot-origin.service --no-pager
sudo journalctl -u nftables-after-docker.service -n 30 --no-pager
```

При удалении доверенного адреса закрываются **новые** соединения. Уже
установленные соединения сохраняются до закрытия/истечения conntrack; для
отзыва самого VPN-доступа удалите или отключите профиль узла. Защита хоста не
заменяет защиту провайдера от объёмной DDoS-атаки и не защищает от захвата root.
IPv6 также не гарантирует отсутствие рекламы или блокировок сервиса.
