## О проекте

VPNBot разворачивает на вашем сервере набор VPN- и прокси-сервисов в Docker и
даёт управлять ими из Telegram: пользователи, ключи и подписки, маршрутизация,
блокировка рекламы через AdGuard Home, сертификаты, резервные копии и
обновления. Кроме полного бота поддерживается **минимальная управляемая нода** —
отдельный сервер выхода, которым основной бот управляет по SSH.

Как развивается этот форк:

- изменения готовятся в диалоге с ИИ-ассистентами (вайб-кодинг) и вручную
  просматриваются перед публикацией;
- каждый выпуск проходит автоматический конвейер GitHub Actions: модульные
  тесты на PHP 8.4/8.5 и Python, сборку всех образов с нуля, проверку
  уязвимостей и секретов в каждом слое образа и полный сетевой стенд —
  установку с нуля, реальный трафик через все протоколы, резервное
  копирование и восстановление, откат;
- образы публикуются только комплектом, прошедшим все проверки, и
  устанавливаются по неизменяемым digest.

Автоматические проверки снижают риск ошибок, но не заменяют аудита кода
специалистом и проверки в вашей сети.

## Возможности

- **Протоколы:** VLESS (REALITY, XHTTP, WebSocket, gRPC, VLESS Encryption),
  Trojan, Shadowsocks (+ Cloak, simple-tls, v2ray-plugin), NaiveProxy,
  Hysteria 2, TUIC v5, AnyTLS, ShadowTLS v3, Mieru, MASQUE, WireGuard,
  AmneziaWG, OpenConnect, OpenVPN, IPsec (IKEv2, L2TP), TeleMT (MTProto и WEB),
  TrustTunnel, DNSTT; каждый протокол можно выключить.
- **Пользователи и подписки:** лимиты трафика и срока, Limit IP и HWID,
  подписки для Xray, sing-box, mihomo/Clash и других клиентов, журнал
  подключений пользователя.
- **Маршрутизация:** правила routes, внешние наборы `.dat`/`.srs`, WARP
  (WireGuard или MASQUE), узлы выхода и группы узлов, выборочный выход через
  IPv6, блокировка рекламы через AdGuard Home.
- **Минимальная управляемая нода:** отдельный сервер выхода без Telegram,
  управляемый основным ботом по SSH, с автоматическим откатом неудачных
  изменений.
- **Обслуживание:** веб-панель, автоматические сертификаты (в том числе при
  закрытом порте 80), резервное копирование и восстановление, обновление
  кнопкой из проверенного комплекта образов, ретранслятор Telegram Bot API.
- **Защита хоста:** профиль nftables с вопросами при установке, защита
  происхождения трафика контейнеров, проверка обновлений перед установкой.

## Требования

- сервер **Ubuntu 22.04/24.04** или **Debian 11/12/13**, вход под `root`,

- исходящий доступ к `github.com`, `ghcr.io` и `download.docker.com`;

## Установка

Этот раздел описывает **полную установку** бота. Для отдельного сервера выхода
без Telegram используйте [установку минимальной ноды](#минимальная-управляемая-нода).

1. Скачайте установщик на сервер (stable — ветка `master`):

   ```shell
   curl -fsSLo /root/init.sh https://raw.githubusercontent.com/axiomshiftbit/vpnbot/master/scripts/init.sh
   ```

   Для ветки разработки замените `master` в адресе на `dev`.

2. Положите токен бота в файл, доступный только root, и запустите установщик —
   `master` (stable) или `dev` (development):

   ```shell
   install -m 600 /dev/null /root/.vpnbot-key
   nano /root/.vpnbot-key          # вставить токен от @BotFather, сохранить
   VPNBOT_KEY="$(cat /root/.vpnbot-key)" bash /root/init.sh master
   ```

   Токен подставляется из файла, поэтому не попадает ни в history, ни в `ps`.

3. Ответьте на вопросы о **профиле nftables**. Если в `/etc/nftables.conf` ещё
   нет профиля VPNBot, установщик предложит поставить его из каталога
   [`nftables/`](nftables/) и спросит:

   | Вопрос | Что вводить |
   |---|---|
   | Внешний интерфейс (WAN) | Имя интерфейса с публичным адресом, например `eth0`; найденное значение подставлено по умолчанию |
   | Публичный IPv4 / IPv6 | Адреса, назначенные этому интерфейсу; `-` — без IPv6 |
   | Порт SSH | Порт, на котором сейчас работает `sshd` |
   | Адреса, с которых разрешён SSH | Ваши IPv4 или сети через пробел; по умолчанию — адрес текущего подключения. Они записываются в список `my_server` |

   Профиль проверяется в отдельном сетевом пространстве, прежние правила и файл
   сохраняются в `/var/backups/vpnbot-nftables/`. После применения установщик
   попросит **открыть новое SSH-подключение** и подтвердить вход: без
   подтверждения в течение 120 секунд прежние правила вернутся автоматически,
   даже если связь с установщиком оборвётся. Отказаться от профиля можно — бот
   будет работать, но без защиты хоста.

   **После установки firewall работает в ограниченном режиме:** порты бота и
   VPN-сервисов открыты только адресам из списков профиля, и клиенты с других
   адресов подключиться не смогут. Добавьте сети своих клиентов — см.
   [Firewall после установки](#firewall-после-установки-ограниченный-режим).

   Вместе с профилем настраиваются журналы nftables в `/var/log/nftables/`
   (rsyslog и logrotate): события разложены по `host.log`, `vpn.log`,
   `docker.log`, `network.log`, `security.log` и `rkn-blacklist.log`, в каждой
   записи — действие правила (`ACTION=DROP/ACCEPT`). Описание —
   `/var/log/nftables/README_RU.txt`, повторная настройка —
   `bash nftables/logging/nftables.sh` (для ноды — `noda.sh`).

4. Дождитесь запуска и проверьте контейнеры: `cd /root/vpnbot && make ps`
   (журналы — `make l`).

5. **Сразу напишите боту `/start` со своего аккаунта Telegram.** Первый, кто
   напишет боту после установки, становится его администратором (записывается
   в `app/config.php`), поэтому не давайте ссылку на бота никому до этого шага.
   Других администраторов можно добавить позже в меню бота.

6. Кроме Telegram, ботом можно управлять из **веб-панели**. Она слушает только
   `127.0.0.1:8090` на сервере и снаружи недоступна; открывается через
   проброс по SSH-порту с вашей машины:
   `ssh -L 8090:127.0.0.1:8090 root@<сервер>`, затем
   `http://127.0.0.1:8090/panel<hash>/` в браузере. Адрес и пароль показывает
   `docker compose exec php php panel.php url` — подробнее в разделе
   [Веб-панель](#веб-панель-управление-ботом-без-telegram).

### Firewall после установки: ограниченный режим

Профиль nftables по умолчанию пускает к боту (HTTPS 443/tcp и udp, HTTP 80) и
к портам VPN-сервисов только адреса из двух списков:

| Список | Файл | Что открывает |
|---|---|---|
| `my_server` | `/opt/maxmind/list/my_server/geoip-ipv4.nft` | ваши адреса из ответа об SSH: SSH, бот и VPN-порты |
| `asn` | `/opt/maxmind/list/asn_nft/geoip-ipv4.nft` | доверенные сети (например, диапазоны провайдеров ваших клиентов): бот, VPN-порты **и SSH** |

Сразу после установки в `asn` лежат примеры из документационных сетей, а в
`my_server` — только адреса администратора, поэтому VPN-клиенты с других
адресов не подключатся. Блок-лист `rkn` старше этих списков; диапазоны Telegram
(`tg`) служат исходящим правилам TeleMT и бота.

Как добавить клиентов:

1. Впишите сети в `elements` списка `asn` (формат — как в примере файла,
   `203.0.113.0/24 : $ASN,` по строке на сеть) или отдельные адреса в
   `my_server`. Учтите, что оба списка открывают и порт SSH; вход по SSH всё
   равно защищён ключами.
2. Проверьте и примените весь профиль одной транзакцией:
   `nft -c -f /etc/nftables.conf && nft -f /etc/nftables.conf`.

Открыть клиентские порты всем адресам (кроме блок-листа), не трогая SSH, можно
в блоке `PUBLIC-VPN-OPTIONS` профиля: раскомментируйте строки нужных сервисов
и примените профиль так же. Порт, изменённый в боте, поменяйте и в
переменных `*_INPUT` в начале `/etc/nftables.conf`.

**Сетевые настройки хоста.** Установщик (полный бот и нода) пишет
`/etc/sysctl.d/97-vpnbot-neighbor.conf` — защита от соседей по сети хостера:
ARP только для своих адресов, без ICMP redirect и source route, по всем
интерфейсам, включая WAN (`scripts/host_hardening.sh`), — и
`/etc/sysctl.d/99-vpnbot-sysctl.conf`: BBR и fq, буферы и очереди TCP/UDP,
таймауты TCP, conntrack, IPv6 без redirect (`scripts/host_sysctl.sh`). Полный
бот получает `net.ipv4.ip_forward = 1`, нода маршрутизацию запрещает
(`98-vpnbot-node-forwarding.conf`). Выключение IPv6 и отказ от RA записаны
закомментированными строками: выборочный IPv6-выход бота без IPv6 не работает.
Docker после установки профиля: `/etc/docker/daemon.json` с `iptables`,
`ip6tables` и `userland-proxy` = `false` (нода — также `ip-forward` = `false`):
порты и NAT контейнеров обслуживает профиль nftables.
Повторный запуск `bash scripts/host_sysctl.sh full` (или `node`) перезаписывает файл.

Код берётся из коммита последнего **опубликованного** комплекта образов ветки,
а не с её вершины: коммит, ещё не прошедший сборку и стенд, на сервер не попадает.

Ключ бота передаётся переменной `VPNBOT_KEY`, а не аргументом: аргумент виден
в `ps` всем процессам хоста и остаётся в history. Установщик записывает ключ в
`app/config.php`; на работающей установке файл не перезаписывается. Файл
`/root/.vpnbot-key` нужен при каждом запуске `init.sh`: храните его с правами
600 или удалите после установки и создайте заново перед следующим запуском.

Повторный запуск на работающей установке не меняет код (его вместе с образами
обновляет бот) и не перезаписывает `app/config.php`, но выполняет `make u`, то
есть пересоздаёт контейнеры. Установка из архива без доступа к GitHub: положите
`vpnbot.zip` рядом со скриптом и запустите ту же команду.

## Обновление

Бот обновляется из своего меню (**Обновить**): код и образы приходят вместе из
проверенного комплекта выбранной ветки (`master` — stable, `dev` —
development). Комплект и образы скачиваются до остановки служб — ошибка
загрузки или нехватка места отменяет обновление, не затрагивая работающий бот.
Образы предыдущего комплекта после обновления удаляются, чтобы не занимать
диск; для ручного отката их можно снова скачать по digest из манифеста
`update/image-bundle.previous.json`.

## Справочник команд

Команды обслуживания выполняются **на нужном сервере от root**. Каталог
стандартной установки — `/root/vpnbot`; путь `/root/init.sh` ниже означает
переданную на сервер копию `scripts/init.sh`. Если вы сохранили установщик
как `/opt/vpnbot/init.sh`, замените только путь к установщику: стандартный
каталог устанавливаемого проекта всё равно `/root/vpnbot`.

### Установка и обновление: какую команду выбрать

| Задача | Команда или действие |
| --- | --- |
| Установить полный бот, stable | `VPNBOT_KEY="$(cat /root/.vpnbot-key)" bash /root/init.sh --mode full master` |
| Установить полный бот, development | `VPNBOT_KEY="$(cat /root/.vpnbot-key)" bash /root/init.sh --mode full dev` |
| Установить минимальную ноду, stable | `bash /root/init.sh --mode node master` |
| Установить минимальную ноду, development | `bash /root/init.sh --mode node dev` |
| Обновить код **и** образы полного бота | В Telegram или веб-панели: **Настройки → Обновить**, выбрать ветку, затем **Обновить бота** |
| Обновить код **и** образы ноды | На основном боте: **Ноды → нужная нода → Обслуживание → Обновить с ветки master / dev** — [как работает](#полное-обновление-ноды-кнопкой) |
| Обновить управляющий код ноды вручную (один раз для старой ноды, установка из архива, отказ кнопки) | `python3 -I /root/vpnbot/scripts/node_setup.py --upgrade-code` — [полная последовательность ниже](#обновление-кода-ноды-с-сервера) |

У `init.sh` поддерживаются ветки `master` и `dev` (по умолчанию `master`),
режимы `--mode full` и `--mode node` (по умолчанию `full`). `--mode` указывается
**перед** веткой. Эквивалент выбора режима — переменная `VPNBOT_MODE`.
`VPNBOT_ARCHIVE=/root/vpnbot.zip` задаёт архив исходников;
`VPNBOT_NODE_CONFIG=/root/node-enrollment.json` — файл публичных параметров
первичной установки ноды. Порядок установки и файл токена описаны
в разделе [«Установка»](#установка); токен Telegram ноде не нужен.

**Перезапуск и обновление версии — разные операции.** `make r`, `make u` и
перезапуск systemd-службы используют выбранный комплект образов. Они не
переводят код на новый выпуск. Отдельной цели `make update` нет.
`update/update.sh` — фоновый обработчик команд меню, а не разовая команда
обновления; вручную записывать запросы в `update/pipe` не требуется.
Повторный `init.sh --mode node` тоже не обновляет установленную ноду:
`node_setup.py` откажет, если её состояние уже создано.

### Полный бот: запуск, остановка и диагностика

Команды `make` из этого раздела выполняются в каталоге **полного бота**:

```sh
cd /root/vpnbot
```

| Команда | Действие |
| --- | --- |
| `make u` | Скачать недостающие образы выбранного комплекта, пересоздать включённые контейнеры и запустить обработчик обновлений |
| `make start` | Как запуск контейнеров в `make u`, но без запуска обработчика обновлений |
| `make r` | Проверить доступность выбранных образов, остановить и снова запустить бот с обработчиком обновлений |
| `make d` | Остановить обработчик обновлений и контейнеры всех профилей этой установки, без удаления томов |
| `make pull` | Проверить выбранный комплект и скачать недостающие образы включённых сервисов, без остановки контейнеров |
| `make preup` | Запустить только фоновый обработчик обновлений; обычно его уже запускает `make u` или systemd |
| `make ps` | Показать состояние контейнеров |
| `make l` | Вывести журналы контейнеров |
| `docker compose logs --tail=100 php` | Последние 100 строк одного сервиса; вместо `php` можно выбрать другой сервис |
| `docker compose logs --tail=100 -f php` | Следить за журналом сервиса; `Ctrl+C` завершает просмотр |
| `sh scripts/diagnose_bot.sh` | Диагностика версии, контейнеров, портов, webhook и журналов; ничего не перезапускает |
| `make webhook` | Запросить сведения Telegram о webhook |
| `make tgapi cmd=status` | Адрес Bot API и ретранслятор Telegram API; все команды — в разделе [Ретранслятор Telegram Bot API](#ретранслятор-telegram-bot-api) |
| `make s` | Краткий Git-статус локальной копии |
| `git rev-parse --short HEAD` | Коммит установленного кода |
| `(umask 077; make backup)` | Сохранить экспорт бота в `backup.json` в текущем каталоге |

`make backup` перезаписывает `backup.json`; файл содержит данные доступа.
Для нового файла `umask 077` задаёт права только владельцу; для ранее
созданного задайте их командой `chmod 600 backup.json`. Восстановление выполняется через
меню бота/панели. Сырые журналы, вывод `make webhook` и диагностического
скрипта могут содержать приватные адреса и данные доступа: не публикуйте их
без удаления конфиденциальных значений.

Для дополнительных операций Compose с учётом выключенных протоколов:
`python3 scripts/protocol_modules.py compose <команда>`; например,
`python3 scripts/protocol_modules.py compose ps`. Изменение настроек протоколов
применяет фоновый обработчик. На минимальной ноде полный Compose и `make u/r`
не используются.

### Полный бот: автозапуск и systemd

| Команда | Действие |
| --- | --- |
| `make cron` | Добавить в cron автозапуск `@reboot cd /root/vpnbot && make r` |
| `make uncron` | Удалить именно эту запись автозапуска |
| `sh scripts/install_as_service.sh` | Установить и включить `vpnbot.service` для текущего каталога; сейчас службу не запускает |
| `systemctl start vpnbot.service` | Запустить установку через systemd |
| `systemctl restart vpnbot.service` | Перезапустить установку, управляемую этой службой |
| `systemctl stop vpnbot.service` | Остановить установку, управляемую этой службой |
| `systemctl status vpnbot.service --no-pager` | Посмотреть состояние службы |
| `journalctl -u vpnbot.service -n 100 --no-pager` | Журнал службы |
| `systemctl enable vpnbot.service` / `systemctl disable vpnbot.service` | Включить / выключить автозапуск службы без немедленного запуска / остановки |

Выберите один способ автозапуска. `init.sh` добавляет cron, если
`vpnbot.service` ещё не включена. При переходе на systemd выполните
`make uncron` после установки службы. Для уже запущенного через `make` бота
сначала `make d`, затем `systemctl start vpnbot.service`. После перехода
управляйте запуском и остановкой через systemd. Без cron или systemd после
перезагрузки поднимаются только контейнеры с собственным `restart`-правилом.

### Нода: команды на её сервере

Эти команды относятся только к минимальной управляемой ноде. Плановое
обновление образов, перезапуск, откат, копирование и восстановление доступны
через **Ноды → нужная нода → Обслуживание** на основном боте; он проверяет
связь после изменения. Локальное обслуживание выполняйте после завершения
операций основного бота.

| Команда | Действие |
| --- | --- |
| `python3 -I /root/vpnbot/scripts/node_setup.py --help` | Все параметры установщика ноды |
| `python3 -I /root/vpnbot/scripts/node_setup.py --upgrade-code` | Установить управляющий код из этой локальной копии, обновить systemd-юниты и согласовать firewall, сохраняя настройки и ключи; образы не обновляет |
| `python3 -I /root/vpnbot/scripts/node_setup.py --controller-key /root/new-controller.pub` | Заменить публичный SSH-ключ основного бота; прежний управляющий ключ теряет доступ |
| `systemctl status vpnbot-node.service --no-pager` | Состояние службы запуска; `active (exited)` нормально для её типа `oneshot` |
| `systemctl restart vpnbot-node.service` | Перезапустить ноду с сохранённым состоянием; незавершённое изменение при загрузке откатывается |
| `systemctl list-timers 'vpnbot-node-*' --all` | Расписание восстановления работоспособности и продления сертификата |
| `systemctl start vpnbot-node-renew.service` | Выполнить штатную проверку/обновление сертификата для транспорта, которому он нужен |
| `journalctl -u vpnbot-node.service -u vpnbot-node-worker.service -u vpnbot-node-renew.service -n 100 --no-pager` | Журналы служб ноды |
| `tail -n 100 /var/log/vpnbot-node/setup.log` | Этапы и безопасные категории ошибок установки/обновления кода; файл доступен только root |
| `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub -E sha256` | Отпечаток публичного ключа сервера для сверки с карточкой ноды |

Для первичной настройки после подготовки пакетов и Git-копии также доступны
параметры `node_setup.py`: `--config /root/node-enrollment.json` вместо
интерактивных вопросов, `--channel latest` (stable, по умолчанию) или
`--channel dev`, `--bundle /root/published-bundle.json` для заранее полученного
манифеста опубликованных образов. `--config`, `--controller-key` и
`--upgrade-code` взаимно исключаются. `--bundle` относится только к первичной
установке; файл не должен быть вручную составленной смесью образов.

Для намеренной остановки сначала остановите таймеры: иначе проверка
работоспособности снова поднимет контейнеры. Дождитесь завершения операций
обновления и выпуска сертификата, затем выполните:

```sh
systemctl stop vpnbot-node-watch.timer vpnbot-node-renew.timer
systemctl stop vpnbot-node-watch.service vpnbot-node-renew.service
systemctl stop vpnbot-node.service
```

Возобновление работы:

```sh
systemctl start vpnbot-node.service
systemctl start vpnbot-node-watch.timer vpnbot-node-renew.timer
```

`stop` не отменяет автозапуск после перезагрузки. `vpnbot-node-worker.service`
запускает основной бот для очереди операций. Режимы `rpc`, `worker`, `boot`,
`watch`, `stop`, `renew` в `node_manager.py` — внутренний интерфейс этих
служб; ручной RPC не заменяет проверку трафика и подтверждение основным ботом.

### Команды в Telegram и веб-панели

В сообщении Telegram поддерживаются следующие команды; доступ к настройкам
определяется правами пользователя. В стандартном списке Telegram бот
регистрирует `/menu` и `/id`, остальные можно набрать вручную.

| Команда | Действие |
| --- | --- |
| `/start` | Открыть главное меню; у нового бота первый пользователь становится владельцем |
| `/menu` | Открыть главное меню |
| `/id` | Показать ID пользователя и текущего чата |
| `/mirror` | Открыть настройки зеркала |
| `/telemt` | Открыть TeleMT; выключенный модуль сначала требует включения |
| `/dnstt` | Открыть DNSTT |
| `/searchLogs IPv4` | Открыть сведения об указанном IPv4 и действия для поиска/обработки его журналов |
| `/debug` | Переключить отладочный режим бота; повторная команда выключает его |

Обновление, перезапуск, резервные копии, SSL, маршруты и управление
пользователями выполняются **кнопками меню**. `/restart`, `/backup`,
`/applyupdatebot` и `/nodeRun …` в исходниках — данные кнопок, а не команды
для ввода сообщением. Веб-панель предоставляет те же меню; её консольные
команды на сервере полного бота:

| Команда | Действие |
| --- | --- |
| `docker compose exec php php panel.php url` | Адрес панели; при первом запуске также выводится созданный пароль |
| `docker compose exec php php panel.php passwd` | Ввести новый пароль без отображения; открытые сессии сбрасываются |
| `docker compose exec php php panel.php admin TELEGRAM_ID` | Добавить администратора по числовому ID; первый в пустом списке становится владельцем |
| `docker compose exec php php panel.php reset` | Очистить ленту панели |
| `ssh -L 8090:127.0.0.1:8090 SERVER_ALIAS` | С административной машины открыть SSH-туннель к панели |

`panel.php` без аргумента равнозначен `url`. Форма `passwd <пароль>` также
поддерживается, но оставляет пароль в истории и аргументах процесса;
используйте интерактивный ввод. Подробности — в разделе [веб-панели](#веб-панель-управление-ботом-без-telegram).

### Консоли контейнеров и остальные цели make

Каждая из следующих команд открывает `/bin/sh` **внутри уже запущенного**
одноимённого Compose-сервиса: `make php`, `make wg`, `make wg1`, `make ss`,
`make ng`, `make np`, `make up`, `make ad`, `make wp`, `make proxy`,
`make telemt`, `make dnstt`, `make hy`, `make xr`, `make oc`, `make service`.
Здесь `make up` — консоль сервиса `up`, запуск установки — `make u`.
Для сервиса без короткой цели: `docker compose exec ИМЯ_СЕРВИСА /bin/sh`.

| Команда | Действие и ограничения |
| --- | --- |
| `make test` | Python/PHP-тесты и проверка синтаксиса PHP; запускать на тестовом хосте из копии исходников, не внутри рабочего контейнера |
| `make versions` | Проверить закреплённые версии, уязвимости и новые выпуски; при необходимости использовать заранее настроенный `GH_TOKEN`, не вставляя его значение в команду |
| `make b` | Локальная сборка образов включённых сервисов; цель для разработки, не штатное обновление сервера |
| `make push` | Намеренно завершается отказом: образы публикует CI |
| `make dv` | **Удаление данных:** Compose down с `-v`, включая тома установки; обработчик обновлений эта цель не останавливает |
| `make reset` | **Сброс:** остановка, `git reset --hard`, `git clean -fd`, удаление томов `vpnbot_adguard` и `vpnbot_warp`, затем запуск; локальные правки и часть данных теряются |
| `make c` | **Откат локальных правок:** предварительно индексирует `config/`, откатывает остальные неиндексированные изменения отслеживаемых файлов и сбрасывает индекс; не обновляет бот |
| `make delete` | **Удаление установки:** остановка, глобальная очистка неиспользуемых Docker-образов и томов, удаление `/root/vpnbot`; затрагивает ресурсы других проектов на хосте |

Последние четыре цели перечислены для полноты существующего `makefile`, а
не как способ обновления. Для обычного обслуживания используйте `make d/r`
или соответствующую службу. Не вызывайте голый `make`: первая цель в файле —
`b`, то есть локальная сборка.

Проверка `make versions` блокирует уязвимость с доступным исправлением
(код 1), а новый выпуск только сообщает. nginx сверяется в стабильной ветке.
Новый пин нужно добавить в `COMPONENTS` или в `UNCHECKED` с причиной в
`scripts/ci_check_components.py`; это проверяет `tests/ci_components_test.py`.

Команды установки, проверки и восстановления защиты происхождения
контейнеров и окна ACME приведены в [Хостовых службах](docs/HOST_SERVICES_RU.md).
Они относятся к полному боту; у минимальной ноды свой профиль firewall.

## Минимальная управляемая нода

Раздел **Menu → Ноды** управляет отдельными серверами по SSH. На основном
сервере остаются Telegram-бот, пользователи, HWID/Limit IP, подписки,
маршруты и AdGuard Home. Нода принимает выбранный трафик и выпускает его в
интернет. Прежний режим полного бота с узлами выхода и локальным IPv6 сохранён.

### 1. Подготовьте основной бот и сервер ноды

Сначала обновите **основной бот** до опубликованного комплекта с меню
**Menu → Ноды**. На другом, чистом сервере нужны Debian/Ubuntu с systemd,
доступ администратора по SSH и назначенные провайдером публичные адреса.
Установщик ставит необходимые пакеты и Docker. Он откажется работать поверх
других запущенных контейнеров; действующий полный бот сначала переносится
отдельно. Команда ниже не преобразует работающий полный бот в ноду.

На ноде проверьте имена интерфейсов, адреса, маршрут и действующий SSH-порт:

```sh
ip -br address
ip -4 route show default
ip -6 route show default
sshd -T | awk '$1 == "port" {print $2}'
```

IPv6 должен быть выдан провайдером и назначен интерфейсу без `tentative` или
`dadfailed`. Шлюз берите из настроек провайдера, не придумывайте его. Если IPv6
отсутствует, оставляйте соответствующее поле пустым и выбирайте IPv4.
Для установки должны быть свободны TCP/443, 8443, 9443, 9444 и 8080;
TCP/80 нужен при выпуске сертификата.

### 2. Создайте карточку и получите установщик

На **основном боте** откройте **Menu → Ноды → Добавить ноду**, задайте имя.
Сохраните показанную строку `ssh-ed25519 …`: это **публичный ключ управления**,
который потребуется установщику. Приватный ключ остаётся у основного бота.

Скачайте установщик на **ноду** и запустите его в режиме ноды:

```sh
curl -fsSLo /root/init.sh https://raw.githubusercontent.com/axiomshiftbit/vpnbot/master/scripts/init.sh
bash /root/init.sh --mode node master
```

Токен Telegram этому режиму не нужен, ключи доступа к GitHub тоже: код
скачивается по HTTPS. Если в `/etc/nftables.conf` нет профиля ноды,
установщик поставит шаблон [`nftables/noda.conf`](nftables/noda.conf) и списки,
а адреса, WAN и порты SSH спросит на следующем шаге (прежний файл сохраняется
рядом как `nftables.conf.before-vpnbot`). Установщик получает код последнего
опубликованного комплекта, прошедшего CI. Для испытаний используется `dev`
вместо `master` (в адресе и в команде); неопубликованные изменения вершины
ветки он не устанавливает.

### 3. Заполните параметры установщика на ноде

| Поле | Что вводить |
|---|---|
| Публичный ключ `ssh-ed25519` | Строку из карточки ноды основного бота, не ключ хоста |
| Адреса разрешённых VPN-серверов | Фактические публичные исходящие IPv4/IPv6 основного бота и других серверов через пробел; без портов и CIDR |
| Адреса администратора для SSH | Ваши публичные исходящие IP через пробел; обязательно включите адрес текущего SSH-подключения |
| Публичные IPv4/IPv6 ноды | Адреса, уже назначенные её внешнему интерфейсу; `-` очищает отсутствующее семейство |
| Внешний интерфейс | Фактическое имя из `ip -br address`, например `eth0` или `ens3` |
| Порты SSH | Уже действующие порты через пробел; установщик проверяет их совпадение с `sshd -T`, а не переносит SSH на новый порт |
| Доверенные IPv6-маршрутизаторы | Подтверждённые link-local адреса шлюзов; нужны для разрешения RA, если сеть получает маршрут через RA |
| Транспорт | `reality`, `ws`, `grpc` или `xhttp`; для начальной настройки можно оставить `reality` |
| Своя заглушка с паролем | `да`, если нужен собственный сайт прикрытия; иначе `нет` |
| Собственный домен | Нужен для своей заглушки и для TLS-транспортов `ws/grpc/xhttp`; DNS должен вести на ноду |
| Домен REALITY | Подходящий сайт маскировки; при своей заглушке используется ваш домен |
| Ядро | `origin` — основное, `origin2/origin3` — сохранённые предыдущие, `fork` — форк с SMUX |
| Семейство выхода | `4` или `6`: с какого адреса нода обращается к сайтам |
| Семейство подключения | `4` или `6`: как основной бот соединяется с VPN на ноде |

Вопросы показывают найденные значения в скобках: Enter сохраняет их, новый
ввод заменяет. WAN, IP и порты определяются по сети ОС и `sshd -T`;
явные списки `node4/node6_sources`, `admins`, `ssh` читаются из установленного
профиля. Текущий источник SSH добавляется в предлагаемый список администраторов.
MyServer/ASN автоматически в этот список не переносятся. `-` очищает
необязательные IP, список IPv6-маршрутизаторов или подсети SSH.

Требуются реальные публичные адреса; адреса для документации и внутренние
сети не подходят. Если соединение проходит через NAT, разрешайте именно
исходящий адрес, который видит нода. Указанные разрешённые источники
закрепляются также для SSH-ключа управления. Расширение списка источников —
административное изменение на хосте, оно не выполняется редактированием
маршрутов в Telegram. При ограничениях в firewall провайдера согласуйте и
этот список доступа.

Профиль nftables ноды — шаблон [`nftables/noda.conf`](nftables/noda.conf),
его ставит `init.sh --mode node`; для полной версии — [`nftables/nftables.conf`](nftables/nftables.conf)
с сетями контейнеров. Установщик ноды согласует профиль с проверенными параметрами:
локальные адреса, WAN, действующие порты SSH, `node4/node6_sources`,
`node4/node6_admins`, `node4/node6_ssh`, `node6_public` и `ipv6_routers`.
Источники VPN и администраторы SSH разделены. MyServer/ASN сохраняются;
дополнительная защита ноды независимо проверяет разрешённые источники,
UID процессов, внутренние сети и временное окно ACME. VPN-клиентам закрыты и
подсети WAN-интерфейса ноды со шлюзами провайдера, даже с публичными адресами:
соседний сервер в той же подсети через ноду недоступен. Список читается из
таблицы маршрутов при каждом применении настроек и загрузке.

До первого применения профиля установщик ноды спрашивает явные IP
администраторов (включая текущий источник SSH), WAN, адреса и действующие порты
sshd и подставляет их в шаблон.
В профиле с `SERVER_SSH_PORTS` эти порты используются для явного доступа;
прежние порты ASN в `NODE_SSH_PORTS` не расширяются.
В конце установки и обновления кода ноды проверяются синтаксис сохранённых
правил и их соответствие работающему фаерволу. При установленном базовом
профиле дополнительно обязательны активная служба nftables и её автозапуск.
Ошибка проверки прерывает установку; автоматического перезапуска nftables нет.
Без базового профиля сохранение защиты ноды обеспечивает `vpnbot-node.service`.

Установщик показывает текущий этап и понятную причину отказа: например,
отсутствующий параметр ядра, сбой DNS/TLS, занятый порт или недостаток места.
Журнал `/var/log/vpnbot-node/setup.log` доступен только root и содержит время,
этап, безопасную категорию ошибки и код завершения команды. Ключи, введённые
значения, аргументы команд и сырые ответы программ в него не записываются.
Если IPv6 полностью отключён в ядре, установка с IPv4 продолжается без
обращения к отсутствующему IPv6 sysctl. Запрет маршрутизации сохраняется
для обоих семейств при загрузке, а доступные параметры проверяются сразу.

Полная версия при подготовке контейнеров определяет стабильные локальные
адреса по маршрутам ОС, обновляет `PUBLIC_IP`, WAN, `node6_public`,
`egress6_snat` для `fd42:7662:6::9` и link-local шлюз действующего IPv6-маршрута.
Существующие доверенные источники сохраняются. Новые IPv6-источники полной
версии задаются явно через `VPNBOT_NFT_SOURCES6` (адреса через пробел):
установщик не может определить, каким удалённым серверам вы доверяете.
Если IPv6-маршрута нет, локальный IPv6-вход и соответствующая запись SNAT
остаются пустыми. Несколько WAN, временный адрес или несовпадение изменяемых
живых правил с профилем требуют проверки администратора и вызывают отказ.

Проверка полной версии без применения:

```sh
cd /root/vpnbot
python3 scripts/nft_host_setup.py --check
```

До изменения выполняется проверка в отдельном сетевом пространстве и
`nft -c`. Установщик меняет только затронутые цепочки/наборы, проверяет
результат чтением из ядра, сохраняет `/etc/nftables.conf.before-vpnbot-setup`
и включает автозапуск nftables. Ошибка записи или потеря процесса запускает
откат; общий `flush ruleset` в самом профиле сохраняется для штатной полной
атомарной загрузки. Правила Docker и отдельные guard-таблицы при подстановке
адресов не сбрасываются. При отсутствии файла используется штатная защита
соответствующего режима с явным сообщением; профиль доступа не угадывается.

### 4. Сверьте ключ сервера и подключите ноду

В конце установки будут показаны пользователь `vpnbot-ctl`, отпечаток
`SHA256:…` и **публичный ключ SSH-хоста ноды**. Через доверенную консоль
провайдера или уже проверенное SSH-соединение их можно получить повторно:

```sh
ssh-keygen -l -E sha256 -f /etc/ssh/ssh_host_ed25519_key.pub
awk '{print $1, $2}' /etc/ssh/ssh_host_ed25519_key.pub
```

В основном боте нажмите **Подключить по SSH**. Введите **одной строкой**:

```text
NODE_PUBLIC_IP SSH_PORT ssh-ed25519 SERVER_PUBLIC_KEY_BASE64
```

Замените обозначения значениями своей ноды. IPv6 вводится без квадратных
скобок; доменное имя вместо IP здесь не принимается. Нужен полный публичный
ключ из двух полей, без комментария в конце; одного отпечатка `SHA256:…`
недостаточно. Это третий ключ: не путайте его с ключом управления из карточки
и ключом хоста GitHub. Автоматически принимать изменившийся ключ нельзя.

Бот проверит SSH и реальную передачу трафика, после чего покажет
**«Нода подключена. Выберите маршруты и пользователей»**. Управляющая учётная
запись не предоставляет обычную оболочку или SSH-проброс портов.

### 5. Настройте firewall, домен и IPv6

Профиль минимальной ноды — [`nftables/noda.conf`](nftables/noda.conf). Установщик
ставит его сам и подставляет интерфейс, SSH-порты, адреса администраторов и
основного бота и IPv6-списки из ваших ответов. Списки `my_server` и `asn` в
[`nftables/list/`](nftables/list/) содержат только примеры — замените их своими
адресами, если используете. Сохраняйте доступ к консоли провайдера при первом
применении firewall.

| Назначение | Входящий доступ |
|---|---|
| SSH хоста | Администраторы, разрешённые серверы и предусмотренные профилем SSH-сети/ASN; совпадение с ASN само по себе не разрешает VPN |
| VPN TCP/443 | Только разрешённые серверы |
| WireGuard UDP/51820, AmneziaWG UDP/51821 | Только разрешённые серверы, когда канал включён |
| HTTP-01 TCP/80 | Временно для внешних ACME-проверок; закрывается после операции, аварийное окно ограничено временем |
| Внутренние TCP/8443, 9443, 9444, 8080 | Не открывать отдельно из интернета |

Установщик ноды сам создаёт собственную таблицу `inet vpnbot_node`,
`/etc/vpnbot-node/guard.nft` и службы её восстановления. Не заменяйте этот файл
пустой заглушкой. Файлы `/etc/vpnbot-telegram/guard*.nft` относятся к отдельному
SSH-прокси Telegram; минимальной ноде без Telegram он не нужен.
`/etc/nftables.d/vpnbot-origin*.nft` относится к защите источников трафика
полного бота. Защита минимальной ноды создаётся её собственным компонентом.
Настройки ОС и firewall провайдера установщик за вас не заполняет.

Для собственного домена заранее настройте A/AAAA на адреса ноды. Не оставляйте
AAAA на недоступный IPv6 и не включайте HTTP/CDN-прокси перед нодой для этой
схемы проверки. В firewall провайдера TCP/80 должен позволять проверку ACME;
локальное временное окно не может открыть порт, закрытый у провайдера.
Сертификат первоначально выпускает установщик, затем проверяет таймер
`vpnbot-node-renew.timer`; вручную — **Обслуживание → Обновить сертификат**.

Три выбора независимы: адрес **SSH-управления**, семейство **VPN-соединения**
и семейство **выхода в интернет**. Например, управление по IPv4, VPN по IPv6
и выход IPv6 допустимы. Для SSH/VPN по IPv6 сначала подготовьте IPv6 основного
бота по разделу [«Выборочный выход через IPv6»](#выборочный-выход-через-ipv6).
На самой минимальной ноде Xray использует сеть хоста: настройки bridge
`br-vpnbot6` и SNAT map полной версии переносить на неё не требуется.
Отказ выбранного IPv6 не означает автоматического перехода на IPv4.

### 6. Выберите маршруты и проверьте результат

В карточке откройте **Маршруты и наборы**, добавьте нужные сервисы, домены,
IP-подсети или наборы правил, затем назначьте **Пользователей**. Начните с
одного тестового пользователя. **Диагностика** должна подтвердить реальный
выход через ноду; обычный SSH-вход этого не доказывает. Проверьте выбранный
сервис с клиентского устройства, обычные назначения вне правила, затем
поведение при отказе ноды. При исходном строгом режиме выбранные назначения
блокируются, а не уходят напрямую.

Параметры транспорта, ядра, шифрования и резервов меняются в **Xray и
подключение**: сначала редактируется черновик, затем применяется целиком.
Дождитесь проверки трафика и завершения операции перед следующим изменением.
Для WireGuard/AmneziaWG сначала разрешите канал, затем выберите его для
связи основного бота; автоматического переключения при DPI-блокировке нет.

Каждый раздел настроек открывается отдельно. «Назад» возвращает в родительское
меню ноды, включая маршруты, наборы и общий реестр DAT. В выборе ядра показаны
версии, полученные с самой ноды. Если версия неизвестна, обновите состояние.

В **IPv4 / IPv6** первая цифра — связь основного бота с нодой, вторая — выход
ноды в интернет: `IPv4 → IPv4`, `IPv4 → IPv6`, `IPv6 → IPv4`, `IPv6 → IPv6`.
Адрес SSH меняется отдельно. В **Домены и сертификат** задайте основной домен
и до 12 дополнительных имён без `https://`, путей и wildcard. Все A/AAAA
каждого имени должны указывать на эту ноду. Имена войдут в один сертификат
и конфигурацию сайта; срок сертификата показывается в карточке.
В **REALITY → Домен REALITY** кнопка «Использовать свой домен» включает свой
сайт прикрытия. Ручной внешний домен в режиме REALITY выключает собственную
заглушку как цель REALITY; новый путь тоже проходит проверку трафика.

В **XHTTP** доступны режим, Mux.Cool для fork и параметры XMUX/HTTP.
`maxConnections` и ненулевой `maxConcurrency` взаимоисключающие: перед
выбором фиксированного числа соединений задайте `maxConcurrency = 0`.
В **WireGuard** настраиваются включение, MTU и Keepalive; в **AmneziaWG** —
также Jc/Jmin/Jmax, S1–S4, H1–H4, I1–I5, padding и таймеры. Проверяются диапазоны,
непересечение H1–H4 и размеры пакетов. Для I1–I5 допустимы CPS-теги
`<b 0xHEX>`, `<r N>`, `<rc N>`, `<rd N>`, `<t>`: не более 1000 случайных байт
на тег и 1400 байт на пакет. `-` очищает поле. Защита cookie остаётся включённой.
Ключ HeaderProtectionKey меняется вместе с ключами AmneziaWG в обслуживании.
В текущем AmneziaWG сочетание RandomTrailers и диапазонов H1–H3 может терять
пакеты ([upstream #186](https://github.com/amnezia-vpn/amneziawg-go/issues/186)).
Бот выключает RandomTrailers при таких диапазонах на сервере и в экспортируемых
профилях. С фиксированными H1–H3 опция доступна в версии 3.1.

**Шаблоны AmneziaWG.** «Шаблоны и генерация» использует тот же генератор,
что полный бот. Сначала выберите версию протокола: **1.5, 2.0, 3.0 или 3.1**.
Для 1.5 доступен Classic, для 2.0 — Standard/Aggressive/Mobile 2.0,
для 3.0 и 3.1 — Standard/Aggressive/Mobile 3.0. Меню показывает только поля
выбранной версии. Выбор создаёт черновик; соединение переключается после
«Применить» и успешной проверки трафика.
Выбор шаблона или «Перегенерировать» готовит новые J/S/H/I и таймеры в черновике.
Проверьте их и нажмите «Применить». Ключи канала при этом сохраняются.
Пресеты I1–I5, в том числе QUIC Initial, доступны отдельно для каждого пакета.

Автогенерация задаётся интервалом 1, 3, 7, 14 или 30 дней; 0 выключает её.
Основной бот применяет свежий шаблон через обычную проверку трафика и откат.
Она заменяет также ручные изменения параметров обфускации. При недоступности
ноды повтор выполняется не чаще раза в час; активная операция, восстановление
или ручной черновик блокируют автоматическое изменение. Основной бот должен
работать. Для ручных параметров без автоматической замены оставьте интервал 0.
В DPI клиента и масках сервера доступны готовые пресеты фрагментации и UDP noise.


Карточка ноды показывает 🟢 при свежем успешном статусе, 🔴 при остановке или
ошибке связи, ⚪ при устаревших данных. Основной бот запрашивает состояние
примерно раз в минуту; дата последней проверки отображается в карточке.
Проверка трафика и уведомления об отказе выполняются отдельно.
Справка находится в конце «Обслуживания» и содержит оглавление.

Остальные строки карточки — измеренные значения, а не оценки. Источник,
который не удалось прочитать, показывается как «нет данных»:

| Строка | Откуда данные |
|---|---|
| Версия ноды | коммит установленного кода (после обновления кнопкой или ручной установки из клона без локальных правок), коммит комплекта, чьи образы сейчас работают, версия ядра Xray; предупреждение, если установленные модули изменены после установки |
| Сервер ноды | `/proc` ноды при проверке: время работы, нагрузка, свободные память и диск, трафик интерфейса с загрузки сервера |
| Подключённые серверы | основной бот и «Серверы для VPN»: установленные TCP-соединения с VPN-портом (`/proc/net/tcp*`) и UDP-обмен WireGuard/AmneziaWG, на который нода ответила (`/proc/net/nf_conntrack`, около 2 минут; на ядрах без этого файла, например Ubuntu, — «UDP: нет данных») |
| Проверка трафика | проба основного бота через ноду: задержка, страна и IP выхода, страна, которую видит YouTube (полная проверка раз в сутки), доступность за 24 ч |
| Трафик через ноду | счётчики Xray основного бота с последнего сброса (сброс — в «Диагностике») |
| Пользователи | пользователи основного бота с маршрутом через ноду и те из них, кто сейчас онлайн на основном боте |

Версию кода, сведения о сервере и соединениях сообщает только код ноды с этой
функцией; на старом коде карточка пишет, что данных нет.

После смены ключей карточка показывает проверенный результат и время операции;
основной бот получает новый профиль автоматически. Отключённый протокол сначала
нужно включить. Общие ключи REALITY/Encryption/ML-DSA влияют и на внешние панели.

На ноде проверьте автоматические службы и состав контейнеров:

```sh
systemctl is-active vpnbot-node.service
systemctl is-enabled vpnbot-node.service vpnbot-node-watch.timer vpnbot-node-renew.timer
systemctl list-timers vpnbot-node-watch.timer vpnbot-node-renew.timer --all
docker ps --format 'table {{.Names}}\t{{.Status}}'
```

`vpnbot-node.service` имеет тип oneshot: состояние `active (exited)` после
успешного запуска нормально. Сразу создайте бэкап **основного бота** через
Telegram и проверьте время снимка ноды в карточке. После плановой перезагрузки
ноды повторите проверку служб, диагностику и передачу трафика. Если настройка
откатилась, сначала проверьте ключ SSH, разрешённые источники, DNS/IPv6 и
совместимость ядер; не отключайте защиту для обхода ошибки.

### Сертификаты и копии ноды

В «Обслуживание → Сертификат» доступны проверка и обычное продление,
принудительный выпуск, выпуск для нового домена, изменение дополнительных
имён и удаление. Обычное продление сохраняет ещё действующий сертификат,
если Certbot не считает его готовым к обновлению; это не показывается как
успешная замена. Принудительный выпуск запрашивает новый сертификат независимо
от срока. Не запускайте его многократно: действуют ограничения удостоверяющего
центра. TCP/80 открывается только на время ACME-проверки, остальные ограничения
firewall сохраняются.

Зелёная отметка о выпуске или обновлении появляется после проверки нового
сертификата в установленной конфигурации и передачи трафика. При ошибке или
несовпадении результата подтверждения нет. Смена домена создаёт черновик
с заглушкой под паролем: направьте все A/AAAA на адреса ноды, проверьте
дополнительные имена и нажмите «Применить». До проверки новая конфигурация
может автоматически откатиться.

Удаление разрешено только после перехода на REALITY с внешним доменом и
выключенной заглушкой. WS/gRPC/XHTTP/Trojan-gRPC с TLS требуют сертификат. Удаление снимает
текущий сертификат и регистрацию Certbot, но не отзывает его в удостоверяющем
центре и не стирает исторические копии, нужные для восстановления.

Пароль заглушки генерируется на ноде из 48 криптографически случайных байт
(384 бита, 64 символа base64url). В NGINX используется HTTP Basic Auth поверх
TLS. В конфигурации хранится только SHA-512 crypt-хеш, исходный пароль не
сохраняется и не выводится. Это закрытый сайт-заглушка, пароль которого не
предназначен для входа администратора. Изменение домена не ослабляет эту защиту.

«Создать копию ноды» сохраняет подтверждённое состояние и проверяет чтение
копии на основном сервере (`/ssh/nodes/<id>/snapshot.json`); файла для
скачивания при этом не появляется. Снимок содержит настройки, сертификат,
ключи и внешние подключения. Это последняя сохранённая копия, которая
обновляется после подтверждённых операций и при общем бэкапе.
«Восстановить сохранённую копию ноды» использует этот снимок; после переустановки
сначала выполните привязку SSH с проверкой публичного ключа нового сервера.

Файл копии одной ноды:

- **«📥 Скачать копию ноды»** — бот делает свежую копию (если нода доступна и
  не занята; иначе берёт последнюю сохранённую и пишет её дату) и присылает
  в **личный чат** файл `node-<имя>-<дата>.json`. В группу файл не отправляется.
- **«📤 Загрузить копию ноды»** — отправьте этот файл в ответ на запрос.
  Бот проверяет формат, контрольную сумму и ключ управления ноды, заменяет
  сохранённую копию и сразу предлагает «Восстановить эту копию» с проверкой
  трафика и автоматическим откатом. До подтверждения нода не меняется.

В файле нет SSH-ключа управления: он подходит только для этой же ноды в этом
основном боте, в том числе после переустановки ОС ноды с прежним ключом
управления. Если потерян сам основной сервер, нужен общий бэкап бота:
Настройки → «сохранить» (файл приходит первому администратору) и
«восстановить» на новом сервере; затем — восстановление копии в карточке ноды.
Оба файла содержат ключи и сертификат — храните их как пароль.

Каждая операция обслуживания содержит пояснение перед подтверждением.
Подробности доступны в «Справка по обслуживанию». «Сменить ключ клиента основного
бота» меняет его VLESS UUID для входа на ноду — это не токен Telegram и не SSH-ключ.

### Состав, обслуживание и восстановление

Обязательный контейнер — Xray. При выборе собственного сайта добавляется
NGINX с заглушкой и паролем, при включении AmneziaWG — его помощник. Полный
Compose с Telegram, панелью и другими VPN-сервисами на ноде не запускается.
Для такой установки предназначен отдельный firewall-профиль
`noda.conf`; профиль полной версии бота имеет другой набор служб.

### Полное обновление ноды кнопкой

Кнопки **Ноды → нужная нода → Обслуживание → Обновить с ветки master** и
**…dev** обновляют ноду целиком: сначала управляющий код на хосте, затем
контейнерные образы. Последовательность на ноде:

1. Нода получает опубликованный комплект образов выбранной ветки (`latest`
   для master, `dev` для dev) — тот, что прошёл CI. Из него берётся коммит.
2. В Git-клоне `/root/vpnbot` выполняется `git fetch` ветки по HTTPS. Коммит комплекта обязан быть в истории ветки; более старый код, чем
   уже установленный, не ставится (ноду с `dev` не откатить кнопкой master).
3. Каталог `scripts/` этого коммита извлекается из объектов Git во временный
   каталог и устанавливается его же `node_setup.py --upgrade-code`: модули в
   `/usr/local/lib/vpnbot-node/`, systemd-юниты, защита nftables, проверка
   Docker и маршрутизации. Рабочее дерево `/root/vpnbot` при этом не
   используется: если в нём нет локальных правок и выбрана та же ветка, оно
   продвигается fast-forward до коммита, иначе остаётся как есть (бот сообщит
   об этом). `git reset`, `git clean` и переключение веток не выполняются.
4. Уже **новым** кодом заменяются образы именно этого коммита. Основной бот
   подтверждает изменение только после проверки трафика, иначе нода
   возвращает прежние образы и конфигурацию.

Настройки, ключи и внешние подключения сохраняются. Коммит установленного
кода показывается на экране «Обслуживание». Если сбой случился при
обновлении кода, образы не меняются и контейнеры продолжают работать; бот
показывает этап отказа (комплект, Git, понижение версии, этап
установщика). Установщик сначала читает все модули и лишь затем записывает
их: отсутствующий или нечитаемый модуль обнаруживается до первой записи.
Если отказ случился уже после
копирования модулей (этапы `firewall`, `verify`), бот сообщает, что новый код
скопирован, а защита nftables не подтверждена; повторное нажатие установит
код заново. Подробности без секретов — в `/var/log/vpnbot-node/setup.log`
на ноде. После устранения причины кнопку можно нажать снова. Прерванное
обновление кода (перезагрузка, `kill`) таймер восстановления ноды завершает
отказом, нода не остаётся занятой.

Требования: стандартная установка из Git (`init.sh --mode node`). Для установки из архива и для ноды, установленной
до появления этой функции, код один раз обновляется вручную по разделу ниже;
до этого кнопки обновляют только образы, и бот об этом предупреждает.
Отдельная служба `vpnbot-node-upgrade.service` запускается только по
запросу основного бота; RPC принимает лишь канал `latest` или `dev`.

### Обновление кода ноды с сервера

Ручной путь нужен один раз для ноды с кодом старше полного обновления
кнопкой, для установки из архива и как запасной вариант при отказе кнопки.
Ручной `--upgrade-code` сбрасывает запись о коммите последнего обновления
кнопкой; следующее обновление кнопкой сравнивает версию с HEAD клона.

Команда применения **уже скачанных** исходников:

```sh
python3 -I /root/vpnbot/scripts/node_setup.py --upgrade-code
```

Она копирует управляющие модули из `scripts/` в `/usr/local/lib/vpnbot-node/`,
обновляет systemd-юниты и перестраивает защиту ноды. Настройки, ключи и
подключения сохраняются. Сама команда **не выполняет Git fetch/pull и не
скачивает новые образы**. `--channel dev` вместе с `--upgrade-code` не выбирает
другую версию исходников, а `--bundle` с ним несовместим.

Чтобы сначала получить код **последнего опубликованного stable-комплекта**,
на сервере ноды со стандартным Git-клоном выполните
весь блок. Здесь намеренно используется SHA опубликованного комплекта:
вершина `master` может уже содержать ещё не выпущенные изменения.

```sh
bash <<'NODE_CODE_UPDATE'
set -Eeuo pipefail
node_stage='подготовка'
trap 'node_rc=$?; printf "ОШИБКА: этап «%s», код %s. Обновление остановлено.\n" "$node_stage" "$node_rc" >&2; exit "$node_rc"' ERR
cd /root/vpnbot
node_branch=master
node_channel=latest

echo '[1/4] Проверка локальной копии'
if [ "$(git branch --show-current)" != "$node_branch" ]; then
    echo 'Выбрана другая ветка. Проверьте ветку и канал обновления.' >&2
    exit 1
fi
if [ -n "$(git status --porcelain --untracked-files=no)" ]; then
    echo 'Есть локальные изменения. Используйте вариант с отдельной копией кода ниже; не удаляйте их ради обновления.' >&2
    exit 1
fi
node_stage='получение опубликованного комплекта'
echo '[2/4] Получение опубликованного комплекта'
git fetch origin "$node_branch"
python3 scripts/image_bundle.py fetch "$node_channel" update/node-code-bundle.json
node_source="$(python3 -c 'import json; print(json.load(open("update/node-code-bundle.json"))["source"])')"
node_stage='проверка и применение коммита'
echo '[3/4] Проверка и применение коммита'
git merge-base --is-ancestor "$node_source" FETCH_HEAD
git merge-base --is-ancestor HEAD "$node_source"
git merge --ff-only "$node_source"
test "$(git rev-parse HEAD)" = "$node_source"
node_stage='обновление установленного компонента'
echo '[4/4] Обновление установленного компонента'
python3 -I scripts/node_setup.py --upgrade-code
echo 'Код ноды обновлён. Теперь обновите её образы через основной бот.'
NODE_CODE_UPDATE
```

Для ноды, уже установленной с ветки `dev`, замените **обе** строки на
`node_branch=dev` и `node_channel=dev`. Блок не переключает ветку и не
откатывает локальные коммиты. При любой ошибке дальнейшие шаги не выполняются.
Для установки из архива сначала доставьте соответствующие опубликованному
комплекту исходники; Git-команды для неё неприменимы.

**Если в `/root/vpnbot` есть локальные изменения.** Например, ранее на сервер
могли быть перенесены исправления установщика или изменены файлы NGINX.
Не используйте `git reset --hard`, `git clean` или принудительное переключение
ради прохождения проверки. Вместо предыдущего блока можно установить компонент
из отдельного Git worktree опубликованного коммита:

```sh
bash <<'NODE_CODE_COPY'
set -Eeuo pipefail
node_stage='подготовка'
trap 'node_rc=$?; printf "ОШИБКА: этап «%s», код %s. Обновление остановлено.\n" "$node_stage" "$node_rc" >&2; exit "$node_rc"' ERR
cd /root/vpnbot
node_branch=master
node_channel=latest

node_stage='получение опубликованного комплекта'
echo '[1/3] Получение опубликованного комплекта'
git fetch origin "$node_branch"
python3 scripts/image_bundle.py fetch "$node_channel" update/node-code-bundle.json
node_source="$(python3 -c 'import json; print(json.load(open("update/node-code-bundle.json"))["source"])')"
git merge-base --is-ancestor "$node_source" FETCH_HEAD

node_stage='создание отдельной копии исходников'
echo '[2/3] Создание отдельной копии исходников'
node_checkout="$(mktemp -d /root/vpnbot-node-code.XXXXXX)"
git worktree add --detach "$node_checkout" "$node_source"
printf 'Коммит: %s\nКаталог исходников: %s\n' "$node_source" "$node_checkout"

node_stage='обновление установленного компонента'
echo '[3/3] Обновление установленного компонента'
python3 -I -B "$node_checkout/scripts/node_setup.py" --upgrade-code
echo 'Код ноды обновлён. Теперь обновите её образы через основной бот.'
NODE_CODE_COPY
```

Для `dev` также заменяются обе переменные ветки и канала. Этот вариант
сохраняет коммит и локальные изменения **основного каталога** `/root/vpnbot`:
обновляется установленный компонент в `/usr/local/lib/vpnbot-node`, поэтому
`git rev-parse HEAD` в основном каталоге продолжит показывать старый коммит.
Новая копия не включает локальные правки старого дерева: если они нужны в
работе ноды, сначала включите и проверьте их в публикуемом выпуске.
После успешного обновления отдельную копию можно удалить командой
`git -C /root/vpnbot worktree remove /root/vpnbot-node-code.XXXXXX`, подставив
**точный каталог, напечатанный блоком**; установленный компонент останется.

Обслуживание выполняйте, когда в основном боте нет активной операции ноды.
Если применение кода отказало, исправьте указанную причину и повторите
`--upgrade-code`: успешное скачивание исходников само по себе не означает,
что установленный компонент обновлён. Этап и причина записываются в
`/var/log/vpnbot-node/setup.log` без значений секретов.

Затем в основном боте откройте **Ноды → нужная нода → Обслуживание →
Обновить с ветки master** (или `dev`) и дождитесь проверки соединения.
`--upgrade-code` образы оставляет прежними; кнопка повторно применит код
того же коммита и обновит образы. Дальнейшие обновления — кнопкой.
При обновлении обоих серверов сначала обновите основной бот. Повторный
запуск `init.sh --mode node` и `make r` для этой процедуры не нужны.

### Сеть и сохранение настроек ноды

При установке публичные адреса основного бота получают доступ к VPN и SSH;
адреса администратора — только к SSH. Вопросы о публичных адресах ноды,
внешнем интерфейсе, действующих портах SSH и доверенных IPv6-маршрутизаторах
заполняют динамическую защиту ноды и существующий базовый профиль nftables.
Адрес ноды должен быть назначен указанному интерфейсу, а порты — совпадать
с настройками sshd. Для VLAN допустимо имя вида `eth0.100`.

nftables ноды задаётся только вручную: контейнеры ноды работают в сети хоста, и
Docker не должен создавать свои цепочки и таблицы и включать маршрутизацию.
Нужны `"iptables": false`, `"ip6tables": false` и `"ip-forward": false` в
`/etc/docker/daemon.json`. Первичная установка ноды дописывает недостающие
ключи сама (прежний файл сохраняется как `daemon.json.before-vpnbot-node`) и
перезапускает Docker; `--upgrade-code` только проверяет их и отказывает с
пояснением. Установщик также выключает пересылку пакетов файлом
`/etc/sysctl.d/98-vpnbot-node-forwarding.conf`. Итоговая проверка отклоняет
установку, если в nftables остались цепочки `DOCKER*` или таблицы `docker-*`:
перезагрузите сервер или заново загрузите `/etc/nftables.conf`. Профиль и
защита ноды принимают MLD-запросы только с link-local адреса и hop limit 1:
без ответа на них коммутатор с MLD snooping перестаёт доставлять ноде NDP.

Другие VPN-серверы добавляйте кнопкой «🛡 Серверы для VPN (без SSH)» в карточке ноды: им доступны
TCP/443 и включённые резервные каналы UDP/51820 (WireGuard), UDP/51821
(AmneziaWG). Внутренние порты и SSH этим списком не открываются. После
обновления исходников ноды команда `python3 -I scripts/node_setup.py --upgrade-code`
согласует также базовый профиль, чтобы он не блокировал разрешённые резервные
каналы. Посторонние таблицы nftables и отдельные списки SSH сохраняются.

Общий бэкап включает архив ключей управления удалёнными нодами. Если ключ
не удаётся сохранить перед удалением, карточка и маршруты остаются на месте:
устраните ошибку хранения и повторите удаление.

**Xray и подключение.** REALITY, WS, gRPC, XHTTP и Trojan-gRPC; выбор ядра, VLESS Encryption,
ML-DSA, маскировка и блокировка торрентов доступны в пределах совместимости
ядра/транспорта. SMUX/h2mux требуют fork-ядро на ноде и основном сервере,
включая WS/XHTTP. Обычный XHTTP XMUX настраивается отдельно. Черновик применяется
одной операцией; основной бот подтверждает изменение только после проверки
трафика, иначе нода автоматически откатывается.

Два семейства адресов выбираются независимо: основной бот → нода и нода →
сайты. Для SSH через IPv6 сначала подготовьте IPv6 основного бота. TLS-отпечаток
Chrome/Firefox относится к основному боту как клиенту ноды; обратные данные
используют уже установленное соединение. Собственный домен и сертификат нужны
для TLS-транспортов и собственного сайта прикрытия. HTTP-01 открывает TCP/80
только на время проверки; ограничения SSH/VPN сохраняются. Собственный сайт
и QUIC не гарантируют обход DPI или отсутствие рекламы.

**Маршруты.** Выбирайте любые сервисы, домены, подсети и пользователей в
карточке. Поддерживаются HTTPS-наборы `.srs`, `.mrs` и Xray `.dat`. Для `.dat`
в меню наборов откройте общий реестр, добавьте `name.dat:https://…`, затем
выберите файл, GeoSite/GeoIP и категории. Можно использовать
`ext:file.dat:category` и `extip:file.dat:category`. Правила применяет основной
бот; файлы не требуется вручную переносить на ноду. Новая управляемая нода
по умолчанию блокирует выбранные назначения при отказе; прямой запасной выход
включается отдельно.

**Резервные каналы.** WireGuard использует UDP/51820, AmneziaWG — UDP/51821 и
переносит внутри защищённое VLESS-соединение. Разрешаются только заданные
источники. Одновременно активен один резервный канал; автоматической смены
протокола при DPI-блокировке нет. Канал выбирается в настройках.

**Внешние панели.** Создавайте отдельные подключения в карточке ноды, до 32
клиентов. Выберите протокол каждого подключения: **VLESS, WireGuard или
AmneziaWG**. У WG/AWG отдельные ключи и адреса; ключ основного бота не выдаётся
панели. Версия и обфускация AWG общие для ноды: после их изменения обновите
профили внешних панелей.

Для VLESS в карточке нажмите **HTTPS-подписка (3x-ui)**: бот
пришлёт личный URL в приватный чат. Основному боту нужны настроенные домен и
SSL. В панели импортируйте этот URL как подписку исходящих подключений;
правила и пользователей панели настройте в ней самой. Подписка выдаёт актуальную
VLESS-ссылку. Также доступны отдельная VLESS-ссылка, JSON outbound и файл base64.

Для WireGuard скачайте **JSON для панели** и добавьте его в исходящие
подключения 3x-ui. Для Amnezia JSON содержит два исходящих подключения:
VLESS и `amneziawg`. Импортируйте оба в настройки Xray панели и направьте
нужные правила на тег VLESS. Поле `sockopt.dialerProxy` связывает их.
Amnezia переносит только соединение к VLESS ноды; произвольный доступ к LAN
через её внутренний адрес не разрешается. Обычный Xray не понимает протокол
`amneziawg`: его обрабатывает сама 3x-ui. Формат проверяется на стабильной
[3x-ui 3.11.0](https://github.com/MHSanaei/3x-ui/releases/tag/v3.11.0).
WG/AWG выдаются файлом JSON: обычная VLESS-подписка не описывает эти каналы.
После смены протокола прежняя VLESS-подписка становится недоступной.

URL содержит отдельный случайный ключ доступа. Не публикуйте его. При смене
транспорта или общих ключей обновите подписку в панели. После смены ключа
конкретного внешнего подключения получите новый URL: прежний перестаёт работать.
При выключении подключения его подписка недоступна; при повторном включении
с тем же ключом работает снова. Удаление подключения отзывает её окончательно.
При незавершённой операции или недоступной ноде сервер вернёт HTTP 503 —
повторите обновление позже. Подписка не выдаёт непроверенную конфигурацию.

Проверьте поддержку выбранного шифрования ядром панели и разрешите её
исходящий IP на ноде. Для SMUX и расширений, которые панель не переносит из
VLESS-ссылки, используйте **JSON outbound** и совместимое fork-ядро. Ключ основного
бота отдельный; отзыв внешнего клиента не меняет его подключение.

**Бэкап через Telegram.** Бэкап основного бота включает маршруты, карточки,
SSH-ключи управления, личные URL внешних подписок и последние подтверждённые снимки нод: настройки,
ключи подключений, сертификаты, внешних клиентов и резервные каналы. У
недоступной ноды сохраняется предыдущая копия с указанным временем. В
«Обслуживание → Восстановить сохранённую копию ноды» выполняется восстановление
с проверкой реального трафика.

После переустановки ОС сначала установите режим ноды с прежним публичным
ключом управления. Выберите **«Привязать SSH после переустановки»**, сверьте
новый ключ хоста и восстановите копию. До завершения восстановления старая
копия защищена от автоматической замены пустыми настройками. При сохранении
адреса и совместимого профиля прежние клиентские ссылки продолжают работать.
Это не образ ОС: адреса, firewall, SSH администратора и сеть нового хоста
настраиваются отдельно. Кэши `.dat/.srs/.mrs` не входят в бэкап — сохраняются
источники и правила, файлы загружаются повторно. Недоступный источник может
помешать восстановлению правил; ошибка показывается, строгий режим сохраняется.
Бэкап содержит данные доступа и требует конфиденциального хранения.

**Передача управления другому основному боту.** Если новый основной бот уже
обслуживает своих пользователей, не восстанавливайте поверх него полный
бэкап старого только ради одной ноды. Заранее включите публичные адреса
обоих контроллеров в разрешённые источники ноды. На новом боте создайте
карточку, сохраните её публичный ключ в обычный файл
`/root/new-controller.pub` на ноде и выполните от root:

```sh
python3 -I /root/vpnbot/scripts/node_setup.py --controller-key /root/new-controller.pub
```

Команда меняет только разрешённый SSH-ключ управления, сохраняя конфигурацию
ноды и внешние подключения; старый управляющий ключ теряет доступ. Подключите
новую карточку по проверенному ключу хоста, назначьте маршруты и проверьте
трафик. Список сетевых источников эта команда не расширяет. После успешного
переноса отключите старые маршруты и отдельно уберите ненужные адреса из
списков доступа хоста. Одновременно управлять одной нодой из двух карточек
не следует.

**AdGuard Home.** Обычно достаточно экземпляра на основном сервере. Второй
экземпляр имеет смысл для самостоятельного DNS-сервиса на ноде; он не входит
в минимальную установку. DNS-фильтрация не гарантирует удаления рекламы
YouTube, доставляемой с тех же доменов, что и видео.
Это ограничение описано в [официальной справке AdGuard Home](https://adguard-dns.io/kb/adguard-home/faq/#are-there-any-known-limitations).

Подробная встроенная справка доступна в списке, карточках нод и в каждом
разделе настроек: VLESS, REALITY, шифрование, SMUX, XHTTP, DPI клиента,
маски сервера, sniffing, торренты, WireGuard, AmneziaWG, домены и IPv4/IPv6.
Кнопка справки стоит перед «Назад» и открывает оглавление с именованными
разделами. Названия технических параметров сохраняются на английском,
пояснения описывают назначение, ограничения и порядок применения.
Отдельная справка внешних подключений объясняет HTTPS-подписку и импорт
JSON с WireGuard/AmneziaWG в 3x-ui.

В REALITY и управлении доменами есть **«Проверить TLS / ALPN h2»**.
Проверка выполняется с ноды для уже применённого сайта, проверяет сертификат,
его имя, TLS и согласованный ALPN. Она не применяет черновик и не меняет
транспорт. Поддержка `h2` выводится только после успешного согласования;
это не заменяет проверку настоящего VPN-трафика.

Диагностика
проверяет доступность, задержку ответа, страну выхода и скорость между
серверами; основной бот уведомляет администраторов о смене доступности.

## Отключение протоколов и отдельные доступы

В **Настройки → Протоколы** можно полностью отключить TeleMT, OpenConnect, OpenVPN,
TrustTunnel и IPsec. Контейнер отключённого сервиса останавливается и удаляется, его меню
скрывается; настройки, сертификаты и доступы сохраняются для повторного включения.
Его процессы освобождают оперативную память и перестают использовать процессор.
Сохранённые образы и настройки продолжают занимать место на диске.
IKEv2 и L2TP/IPsec имеют отдельные переключатели, но используют один контейнер:
он удаляется, когда выключены оба, либо общий переключатель IPsec.
Существующие протоколы при обновлении остаются включёнными.

TrustTunnel показывает активные сессии и переданный/полученный трафик в карточке
пользователя. Список разбит по 20 пользователей; доступны обновление и справка.
Метрики TrustTunnel 1.1.0 читаются через SSH с `127.0.0.1:1987` внутри контейнера,
без публичного порта. Счётчики относятся к текущему запуску ядра и сбрасываются
при перезапуске; это не постоянный учёт или квота. Ручная настройка `metrics`
сохраняется, отсутствие данных явно отображается в карточке.

MASQUE переключается кнопкой **🟢/🔴 MASQUE** в этом же списке.
Кнопка **Настройки** рядом открывает параметры и доступы, в том числе при
выключенном сервисе. Оба выключателя MASQUE синхронизируют состояние сервиса
и контейнера; повторное включение сохраняет индивидуальные запреты и лимиты.

TeleMT **3.5.17** выключается вместе с MTProto и WEB-прокси. Секреты пользователей,
их индивидуальные запреты и настройки WEB сохраняются. При ручном управлении Docker
бот останавливает ядро; контейнер останавливает администратор. После включения и
пересоздания контейнера сохранённый конфиг запускается автоматически. Отключённый
TeleMT остаётся выключенным после перезапуска контейнера.

В **TeleMT → WEB** доступны **HTTP-метод** (`POST` / `PUT`, TeleMT 3.5.12+)
и **Конвейер WEB** (TeleMT 3.5.13+). По умолчанию используются `POST` и включённый
конвейер. `PUT` может улучшить повторное использование соединений в Linux WebKitGTK.
Конвейер согласует с клиентом до четырёх параллельных HTTP-запросов с сохранением
порядка и защитой от повторной передачи данных. Оба параметра относятся к HTTPS
и HTTPS-lanes; WebSocket сохраняет прежнее поведение. Ссылки остаются прежними,
изменение при включённом WEB переподключает всех пользователей TeleMT.

**TeleMT → WEB → Сайт-приманка** задаёт, что получает запрос к WEB-хосту без
секрета. По умолчанию это встроенная страница. Вместо неё TeleMT может передавать
такие запросы на ваш сайт во внутренней сети: `http://адрес[:порт]`, без пути.
Сайт на самом сервере доступен из контейнера по адресу шлюза `10.10.0.1`.
С TeleMT 3.5.14 вместо IP можно указать имя хоста: оно разрешается при запуске
TeleMT и закрепляется до следующего перезапуска. Пока имя не разрешается, TeleMT
не запускается целиком, поэтому для независимости от DNS указывайте IP.
Всё, что отвечает по этому адресу, становится доступно из интернета под именем
WEB-хоста. Бот не принимает адреса сервисов самой сборки (`10.10.x.x`, кроме
шлюза), loopback, link-local и публичные адреса, порт `8080` и сайт, который
перенаправляет на сам WEB-хост; перед сохранением он проверяет из контейнера
TeleMT, что адрес отвечает по HTTP. Если TeleMT с новым адресом не запустился,
бот сам возвращает встроенную страницу.

Персональные ограничения TeleMT находятся в **Пользователи → имя → Квота / Limit IP**.
Квота задаётся в GiB и суммирует передачу и приём через MTProxy и WEB; `0` означает
безлимит. Изменение действующей квоты сохраняет расход, включение из безлимита
начинает новый период. Сброс расхода требует подтверждения. Кнопка **Период сброса
квоты** (TeleMT 3.5.15+) включает автоматический сброс расхода ежедневно, еженедельно
или ежемесячно по UTC; включение и смена периода текущий расход сохраняют, после
простоя сервера применяется только последний пропущенный сброс. Limit IP ограничивает одновременно активные адреса одного
пользователя, а не число устройств. Оба ограничения выключены по умолчанию.
Кнопка **Запрет подсетей** (TeleMT 3.5.17+, `[access.user_source_deny]`) задаёт
до 32 адресов или подсетей CIDR, с которых этот пользователь не подключится:
ядро отклоняет такое подключение после проверки секрета так же, как неверный
секрет. Остальные пользователи не затрагиваются; `-` снимает запрет. Со старым
ядром список сохраняется, но в конфигурацию не попадает.

В списке пользователей TeleMT и в карточке пользователя видно, кто подключён
сейчас (число соединений и адреса) и сколько трафика прошло — приём и передача
суммарно, раздельно ядро их не считает. Если задана квота, карточка показывает
расход и размер квоты, а исчерпанная квота отмечена в списке знаком ⛔. Кнопка **лог подключений** в карточке
показывает адреса, с которых приходил пользователь: первое и последнее
появление и число подключений (новым считается появление после паузы в
5 минут). Бот опрашивает ядро раз в 20 секунд и сам накапливает трафик, потому
что счётчик ядра обнуляется при каждом его перезапуске; до 20 секунд трафика
перед перезапуском могут не попасть в учёт. Журнал хранится 30 дней, не больше
50 адресов на пользователя, в `config/telemtactivity.json` (доступен только
root) и в резервную копию не входит. За MTProxy-relay виден адрес relay, а не
клиента. Для учёта управляющий API ядра включён всегда — только на loopback
внутри контейнера и только на чтение.

Для лимитов требуется **обновить образ и контейнер TeleMT**. Применение ограничений
переподключает всех пользователей TeleMT. Расход сохраняется при штатной остановке,
в резервной копии бота и дополнительными контрольными записями примерно раз в
секунду. При аварийном выключении возможна потеря расхода после последней записи.
Не удаляйте `config/telemt/data`: при отсутствии или повреждении состояния доступы
с квотой автоматически с нуля не запускаются. Подробности и ограничения учёта IP
описаны в отдельной справке меню. Выбранный relay относится только к MTProxy;
WEB-ссылка использует прямое подключение.

В **Hysteria → Персональные доступы** можно создавать пользователей с отдельной
ссылкой и QR, менять реквизиты, задавать срок в UTC и общую квоту upload + download
в GiB. Резервная копия сохраняет пользователей, ограничения и накопленный расход.
Для этой возможности нужен обновлённый образ Hysteria; версия ядра закреплена
на **2.13.0**. Настройки TLS, Salamander и существующие общие ссылки сохраняются.
Общий пароль даёт отдельный доступ без персональных ограничений: после перевода
клиентов его можно отключить отдельной кнопкой с подтверждением.

В меню Hysteria есть **справка** на русском языке по всем кнопкам: подключение, общий пароль и
персональные доступы, маскировка, обфускация и скорость, смена портов, relay,
диагностика. Смена портов, свой сайт маскировки и полоса выключаются ответом `0`.

В **Hysteria → Тонкие настройки** собраны параметры ядра 2.8–2.13:

- **obfs** — тип обфускации: `salamander` либо `gecko` (экспериментальная, ядро
  2.9.2+), которая дополнительно дробит рукопожатие QUIC. Тип уходит в
  `hy2://`-ссылку; Gecko понимает только официальный клиент Hysteria 2.9.2+,
  и после смены типа всем клиентам нужна новая ссылка.
- **cc** — контроллер перегрузки, когда полоса (Brutal) не задана: `bbr`,
  `bbr-conservative`, `bbr-aggressive` или `reno`. Настройка серверная.
- **Компенсация потерь Brutal** и **игнорирование полосы клиента**: первая
  действует только при заданной полосе, вторая не даёт клиенту выпросить себе
  Brutal в ущерб остальным.
- **sniff** — сервер достаёт домен из HTTP, TLS и QUIC и резолвит его через
  AdGuard сам, поэтому фильтры AdGuard действуют и на запросы по готовому IP.
  Защитный ACL (адреса контейнеров и частные сети) продолжает действовать и
  для имён, которые резолвятся в такие адреса.

Не реализованы намеренно: ECH (нужны ключи и поддержка в клиентах), mimic
(маскировка под TCP требует модуля ядра на сервере и у клиента), Realms (сервер
за NAT), встроенный диапазон портов (смена портов уже делается правилом nft).

Ограничения Hysteria проверяются примерно раз в секунду, поэтому между проверками
возможен перерасход. Отзыв доступа, смена реквизитов и достижение срока или квоты
перезапускают ядро, закрывая все активные соединения; остальные пользователи
переподключаются. При повреждённом состоянии пользователей сервис прекращает
передачу трафика до исправления данных. Файлы резервных копий содержат секреты
доступа и должны храниться в закрытом месте.

В этом же меню настраиваются дополнительные сервисы. У каждого свои
доступы, секреты, токены машинных подписок, сроки, лимиты и счётчики. Новые
сервисы по умолчанию выключены; обновление само их не активирует.

| Сервис | Внешний порт по умолчанию | Экспорт и особенности |
|---|---|---|
| AnyTLS | 443/TCP, отдельное SNI | sing-box, mihomo, `anytls://`, QR; сертификат должен покрывать SNI |
| Mieru | 24445/TCP или UDP | официальный mieru, mihomo, `mieru://` и `mierus://`; оба транспорта передают TCP и UDP приложений, TLS не используется |
| TUIC v5 | 9443/UDP | полный профиль sing-box/mihomo; независимые UUID и пароль, TLS, 0-RTT выключен |
| ShadowTLS v3 + SS2022 | 24447/TCP | полный профиль sing-box/mihomo; отдельные пароль ShadowTLS и личный ключ SS2022; строгий режим TLS 1.3 |
| MASQUE | 24449/TCP и UDP | нативный JSON Xray 26.9.30+, CONNECT-IP через HTTP/3 или HTTP/2; TLS 1.3 |

**443/UDP остаётся за OpenConnect.** На 443/TCP существующий NGINX различает
протоколы по SNI; AnyTLS требует собственного имени, не занятого OpenConnect,
REALITY, NaiveProxy или основным сайтом. Для AnyTLS/TUIC сначала задайте адрес
и SNI, затем обновите SSL в настройках. Для ShadowTLS SNI — имя доступного
сайта прикрытия с TLS 1.3; переносить его сертификат в контейнер ShadowTLS не требуется.
Внутренний Shadowsocks этой связки доступен только через loopback контейнера.
Существующий SS с Cloak/v2ray-plugin сохраняется отдельно.

При первой настройке AnyTLS и ShadowTLS выбирают собственный сайт из основного
домена установки. AnyTLS автоматически формирует стабильный поддомен; DNS должен
направлять его на VPS через wildcard, A/AAAA или CNAME, а сертификат — покрывать
это имя. Произвольные DNS-записи у регистратора бот без доступа к DNS не создаёт.
Обычный HTTP-запрос к AnyTLS показывает основной сайт через проверяемый HTTPS,
в том числе когда активных VPN-доступов нет. ShadowTLS использует TLS 1.3 этого
же сайта. Внутренний маршрут к NGINX не требует нового внешнего порта.
Сохранённые ручные настройки не меняются: перейти на свой сайт можно кнопкой
**Прикрытие своим сайтом · авто**. В этом режиме смена основного домена меняет
адреса прикрытия; новый поддомен также должен входить в DNS и сертификат.
Кнопки включённых протоколов доступны в главном меню.

В TUIC блокировка внешнего UDP прерывает весь туннель, включая TCP приложений.
Доступны режимы UDP `native`, `quic` и расширение `udp_over_stream` для
sing-box/Mihomo. При включении последнего поле обычного UDP relay mode
исключается из профиля; кнопка обычного режима выключает расширение. ShadowTLS по
умолчанию работает только с TCP и отклоняет UDP. Отдельный переключатель
включает проверяемую связку UoT v2; внешний UDP-порт SS при этом не открывается.
Обычный `ss://` без внешнего слоя не является профилем ShadowTLS.

Доступ можно переименовать, выключить, удалить, ограничить по сроку/расходу
или сменить его секреты. Ротация также меняет URL подписки. Имя не меняет
идентичность доступа. Срок проверяется раз в секунду, расход — примерно раз
в 5 секунд: возможен перерасход между опросами. Отзыв и изменение авторизации
перезапускают ядро соответствующего протокола и прерывают его остальные сессии.
Клиенту TUIC может понадобиться время на завершение старой QUIC-сессии и
переподключение. При недоступной статистике доступы с квотами закрываются
после контрольного интервала; неизвестный расход не подменяется нулём.

Mieru дополнительно поддерживает собственную квоту ядра за последние N дней
в МиБ. Она независима от общего лимита в байтах. Сброс общего расхода не
обнуляет историю периодической квоты; точность её порога задаёт ядро Mieru.

У персональных доступов Hysteria и самостоятельных доступов четырёх новых
протоколов есть **Календарь и уведомления**: сброс расхода каждый день, неделю или
месяц с первой датой в UTC, предупреждения администратору о проценте расхода
и приближении срока. По умолчанию расписание и предупреждения выключены.
Месячный сброс сохраняет исходное число: после 31 января идут последний день
февраля и 31 марта. После простоя выполняется один сброс с переносом следующей
даты в будущее. Сброс не продлевает срок и не включает доступ, выключенный
вручную. Недоступная статистика откладывает предупреждение о трафике;
неудачная отправка повторяется в следующем цикле. Расписания и пороги входят
в резервную копию. Связанные доступы VLESS используют общий лимит и его расписание.

**Групповые действия** в этих списках позволяют выбрать до 20 пользователей,
продлить срок, изменить общую квоту, отключить доступ или сбросить расход.
Перед подтверждением видны изменения и причины пропусков. Просмотр действует
10 минут; изменение данных выбранного пользователя требует нового просмотра.
Связанные доступы VLESS управляются из общей карточки и в таком списке пропускаются.

Кнопка **Диагностика** в Hysteria и новых сервисах показывает состояние
контроллера, применение настроек, время успешной проверки и запуска в UTC,
срок сертификата TLS и причину ошибки: сертификат, порт, ядро или конфигурация.
Данные времени доступны после запуска обновлённого контроллера. Карточка
подписки VLESS показывает общий расход с учётом связанных протоколов,
остаток квоты, срок и статус доступа перед ссылками импорта и файлами.

Для AnyTLS, Mieru, TUIC и ShadowTLS доступны прямой выход и выход через имеющийся WARP.
Последний требует работающего WARP; при его отказе прямой обход не включается.
Серверный SOCKS5 WARP передаёт только TCP приложений: UDP в AnyTLS, Mieru,
TUIC и ShadowTLS при таком выходе отклоняется. У отдельного Shadowsocks
тумблер WARP также направляет через него только TCP, а UDP продолжает идти
напрямую — это поведение ядра Shadowsocks, указанное в меню.
Доступ к служебным и приватным адресам блокируется. Профили создают локальный
SOCKS/HTTP-прокси на `127.0.0.1:1080`; настройку системного VPN/TUN выполняет
клиентское приложение. Машинные ссылки содержат секрет доступа: их нельзя
публиковать. Отдельная HTML-страница подписки не создаётся.

В карточке пользователя кнопка **Подписки** выдаёт личные URL. Для Mihomo это
удалённый YAML-профиль; **Provider YAML · XKeen** создаёт записи `proxy-providers`
и `proxy-groups` для существующей конфигурации. Provider загружает прокси раз
в час. Объедините записи с существующими разделами и выберите созданную
группу в правилах. ShadowTLS сохраняет внешний TLS и внутренний SS в одном
профиле. Приложения sing-box поддерживают удалённые JSON-профили; CLI ядра
сам HTTP-профили не обновляет. Нативный Mieru получает JSON для
`mieru apply config <файл>` либо `mieru://`/`mierus://` для импорта;
автоматическая HTTP-подписка для Mieru доступна через Mihomo.

Ссылка отдаёт текущие параметры после их применения сервером. Отключение,
удаление, срок и квота закрывают выдачу; ротация секрета меняет также токен URL.
Сохранённый клиентом файл не исчезает после HTTP-отказа, поэтому отзыв
проверяется также серверным ядром. Сбой применения возвращает HTTP 503 с
`Retry-After`, неизвестный токен или relay — HTTP 404.

**Relay** настраивается в существующем разделе relay отдельно для каждого
протокола: адрес и внешний порт. Кнопка Relay в карточке пользователя выдаёт
файлы, YAML и подписки с этим адресом. SNI, пароли и шифрование остаются
исходными. Пересылку администратор настраивает на relay-сервере:
AnyTLS/ShadowTLS требуют TCP, TUIC — UDP, Mieru — выбранный TCP либо UDP.
TLS завершает VPN-сервер. Поля прежних протоколов и общие порты автоматически
не подставляются. Удаление relay закрывает его URL; скрытого перехода на
прямой адрес нет. URL подписки ведёт к боту, адрес relay находится в профиле.

**Дополнительные настройки** разделены на сервер, общие параметры клиентов и
параметры конкретного клиента. Любой параметр или группу можно сбросить.
Серверные параметры не распространяются автоматически на клиентские:
рисунок трафика Mieru можно задавать независимо с каждой стороны.
Неизвестные поля и несовместимые значения отвергаются до записи.

| Протокол | Дополнительные настройки |
|---|---|
| AnyTLS | Padding, интервалы и число простаивающих сессий, metadata, UDP, повторное использование сессий Mihomo, ALPN и TLS, TCP keepalive/MPTCP |
| Mieru | Multiplexing, handshake mode, traffic pattern: seed, fragmentation, nonce, padding, low entropy; MTU нативного клиента/сервера, DNS, журналирование, метрики и тайм-аут простоя TCP |
| TUIC v5 | Congestion, UDP-over-stream, heartbeat, 0-RTT, таймауты, окна QUIC, число потоков, размер пакета/PMTU; отдельные параметры QUIC Mihomo |
| ShadowTLS v3 + SS | TLS fingerprint и ALPN клиента, соединение с сайтом прикрытия, UoT v2, согласованное мультиплексирование SS (h2mux/smux/yamux, padding, ограничения соединений и потоков) |

В Mieru 3.39.0+ параметр «Сервер → advancedSettings → tcpIdleTimeout»
закрывает TCP-соединение после простоя от `1m` до `24h` (например, `15m`).
По умолчанию он выключен; кнопка «Сбросить» выключает его снова. Данные любого
потока и служебные пакеты клиента продлевают таймер. UDP-транспорт не затрагивается,
выданные профили менять не нужно. Настройка входит в резервную копию. Перед
ручным возвратом на версию Mieru ниже 3.39.0 сбросьте её: старое ядро не знает этого поля.

Browser fingerprint (`chrome`, `firefox`, `edge`, `safari`, `ios`, `random`)
доступен для AnyTLS и ShadowTLS на клиенте. `default` оставляет выбор клиенту.
Mieru не использует TLS; TUIC использует QUIC, для которого uTLS sing-box
не поддерживается. Нельзя назначать им Chrome по аналогии с VLESS.
Для TCP-клиента sing-box доступны TLS `record_fragment`, `fragment`, `spoof`
и проверка SPKI; параметры применяются только к этому формату.
`spoof` требует сетевых привилегий **на клиенте**, capabilities серверов не
расширяются. Смена ключа сертификата требует обновления явно заданного пина.

Маскировка не гарантирует обход любого DPI. Фрагментация и padding увеличивают
расход/задержку; low entropy Mieru расширяет данные примерно в 1.15–2 раза.
0-RTT TUIC по умолчанию выключен из-за риска replay. Для собственного сайта
AnyTLS сохраняется ALPN `http/1.1`. ECH требует управления ключами и
согласованного внешнего SNI для маршрута 443: в текущую схему общего
NGINX/сайта он не включён. Wildcard SNI ShadowTLS, отключение проверки
сертификата и произвольные listeners/routes/private keys через дополнительные
поля не разрешены. Они меняют схему доступа или управляются ботом отдельно.
Если короткий URI не передаёт выбранные параметры, бот предлагает полный
поддерживаемый профиль.
Мультиплексирование ShadowTLS по умолчанию выключено; при включении без
явного выбора транспорта используется `smux`. Для `h2mux` нужен клиент с
исправлением [GO-2026-4918](https://pkg.go.dev/vuln/GO-2026-4918): официальный
Mihomo 1.19.34 ещё включает затронутый `golang.org/x/net`. В образе бота
эта зависимость обновляется при сборке; для внешнего клиента проверяйте его сборку.

Для службы управления на хосте нужен Python 3.9 или новее; установщик
`scripts/init.sh` устанавливает пакет `python3`.

Запускайте и перезапускайте установку через `make u`, `make r` или штатную
службу; новую версию кода и образов устанавливайте кнопкой обновления бота.
Эти пути учитывают сохранённые выключатели при загрузке образов и запуске.
Для дополнительных операций Compose используйте
`python3 scripts/protocol_modules.py compose <команда>` из каталога установки.
Прямой запуск Compose с явно выбранным профилем может включить соответствующий
сервис независимо от меню. Изменения применяет `update/update.sh`; при ошибке
меню показывает ожидание применения, а новый неподтверждённый порт не выдаётся
в машинной подписке.

Первый штатный запуск после обновления дополняет стандартную команду остановки
systemd-службы `vpnbot.service` опцией `--profile '*'`, чтобы остановка охватывала
все контейнеры. Остальные параметры юнита сохраняются; исходная копия находится
в `update/vpnbot.service.before-protocols`. При ошибке `daemon-reload` исходный
файл восстанавливается. Миграция относится к стандартной команде службы этой
установки; собственную команду остановки администратор настраивает с учётом
[профилей Compose](https://docs.docker.com/compose/how-tos/profiles/).

Состояние хранится в `config/protocols/<протокол>/`, переключатели — в
`config/protocol-services.json`. Штатная резервная копия и обновление сохраняют
эти данные. Ядра читают настройки и доступы из каталога только для чтения;
запись разрешена в `runtime/` для счётчиков, статуса и рабочих файлов.
Каталоги имеют закрытые права и не входят в Git. AnyTLS/TUIC получают
только выбранную пару TLS-файлов через закрытое зеркало в
`update/protocol-certs/`; его обновляет служба управления. Сами исходные
сертификаты, включая выбранные нестандартные пути, входят в JSON-бэкап;
при восстановлении проверяется соответствие сертификата приватному ключу.
Перед откатом сохраните полный backup и рабочие файлы установки; старый код
без новых сервисов не сможет управлять их доступами.

Форматы сверяются с документацией [AnyTLS](https://sing-box.sagernet.org/configuration/inbound/anytls/),
[Mieru](https://github.com/enfein/mieru/tree/v3.39.0/docs),
[TUIC](https://sing-box.sagernet.org/configuration/inbound/tuic/),
[ShadowTLS](https://sing-box.sagernet.org/configuration/inbound/shadowtls/) и
[mihomo SS/UoT](https://wiki.metacubex.one/en/config/proxies/ss/).
Версии и SHA-256 архивов закреплены в `.env` и передаются в Dockerfile через
Compose. AnyTLS, TUIC и ShadowTLS используют образ
`ghcr.io/axiomshiftbit/vpnbot-protocol:dev` с sing-box и API статистики, но работают
в трёх отдельных контейнерах. Mieru использует
`ghcr.io/axiomshiftbit/vpnbot-mieru:dev` с сервером mita.
`SINGBOX_VERSION=v1.14.4` управляет ядром трёх протоколов и утилитой PHP;
`MIHOMO_VERSION=v1.19.34` — утилитой PHP; `MIERU_VERSION=v3.39.0` — mita.
`PROTOCOL_GO_VERSION` выбирает Go для сборки серверов и вспомогательных утилит. TUIC v5 и ShadowTLS v3
обозначают версии протокола, а не исполняемого файла.

Чтобы выбрать стабильные версии вместе с проверяемыми контрольными суммами:

```bash
python3 scripts/update_protocol_versions.py --singbox v1.14.4 --mihomo v1.19.34 --mieru v3.39.0
# Проверить текущие стабильные релизы без изменения файла:
python3 scripts/update_protocol_versions.py --singbox latest --mihomo latest --mieru latest --dry-run
```

Без `--dry-run` скрипт меняет только соответствующие публичные пины `.env`,
проверив официальные релизы и SHA-256 ассетов. Остальные значения не выводятся.
`SINGBOX_SHA256`/`MIHOMO_SHA256` относятся к готовым Linux amd64 утилитам;
`SINGBOX_SOURCE_SHA256`/`MIHOMO_SOURCE_SHA256`/`MIERU_SOURCE_SHA256` — к исходникам.
PHP-утилиты теперь собираются из исходников; суммы готовых upstream-ассетов
сохраняются для независимой проверки релиза. Остальные Go-источники закреплены
в `dockerfile/go-sources.sha256`. Исправления зависимостей перечислены в
`dockerfile/go-security.sh`: они не добавляют отсутствующие модули и не
понижают уже более новые версии upstream.
Смена версии без согласованной суммы остановит сборку. Патчи применяются без
fuzz, затем запускаются их Go-тесты; совместимость нового релиза нельзя
гарантировать одной сменой номера.

Правка `.env` **на сервере не меняет скачиваемый готовый образ**. Для обычного
обновления измените пины в репозитории, соберите образы CI в своей ветке и
обновите бот после успешного завершения CI. Каждый выпуск содержит все 18
образов, включая общие образы нескольких протоколов.
Для самостоятельной сборки используйте отдельную рабочую копию без активного
манифеста выпуска:
`python3 scripts/protocol_modules.py compose build php anytls mieru`.
Образ `anytls` общий также для `tuic`/`shadowtls`. Не запускайте `pull` поверх
своей сборки, если не хотите заменить её образом из registry.
В `docker build` без Compose действуют ARG по умолчанию.
Версии записываются в labels `io.vpnbot.*.version` образов; фактические бинарники
проверяются командами `sing-box version`, `mita version`, `mihomo -v`
в соответствующем контейнере.

В этой сборке `dockerfile/protocol-policy/` повторяет правила разрешения DNS
и запрета адресов для каждого UDP-пакета: смена назначения внутри одной
ассоциации, в том числе UoT, не обходит сетевые ограничения. Проверенный IP
фиксируется до передачи пакета выбранному выходу. UUID доступа TUIC скрывается
в сообщениях об ошибках авторизации, в том числе после отзыва доступа.
Для Mieru поверх закреплённых официальных исходников применяется небольшой
патч `dockerfile/mieru-policy/`: он проверяет конечный IP после DNS и каждый
UDP-пакет, включая пересылку через WARP. При таком выходе имя сначала разрешает
DNS-резолвер VPS; прокси получает уже проверенный IP. При сборке запускаются
регрессионные тесты запрета приватных адресов и повторного разрешения DNS.

## Xray 26.9.30, REALITY и VLESS Encryption

Новое рукопожатие REALITY и VLESS Encryption — независимые настройки.
Отпечаток — настройка клиента: сервер его не хранит и не сверяет, значение из
меню попадает в ссылки и подписки всех клиентов как есть. Mihomo для REALITY
дополнительно получает `reality-opts.support-x25519mlkem768: true`. Бот не
подменяет выбор: отпечатки, которые текущее ядро не примет, отмечены в меню ⚠,
а при выборе такого бот предупреждает.

Замер на стенде профилями, которые выдаёт сам бот (2026-10-19; ядра сервера
26.10.17, 26.10.10, форк 26.10.13 с флагом и без; клиенты Xray 26.9.30 и
26.10.17, Mihomo 1.19.32, sing-box 1.14.3):

| Сервер | Клиент на Xray | Mihomo | sing-box |
|---|---|---|---|
| REALITY, требует ML-KEM: Xray 26.9.8 и новее, форк с «Требовать ML-KEM» | chrome, firefox, safari | только chrome | профиль с заменой узла (см. ниже) |
| REALITY, форк без флага | ещё ios, edge, qq | ещё firefox, safari, ios, edge, qq | ещё firefox, safari, ios, edge, qq |
| WebSocket | все из списка | все из списка | все из списка |
| gRPC, XHTTP | все, кроме android и 360 | все, кроме android и 360 | gRPC — все, кроме android; XHTTP — профиль с заменой |

`android` и `360` с REALITY не работают нигде (в этих образцах нет TLS 1.3),
а с gRPC и XHTTP — у Xray и Mihomo: их ALPN не предлагает HTTP/2 (uTLS ставит
свой список поверх профиля), nginx согласует http/1.1. Меню отмечает их ⚠.
sing-box, которому сервер не подходит (REALITY с ML-KEM, XHTTP), получает в
подписке вместо узла Xray другие включённые протоколы;
`random` берёт образец при запуске клиента: стабилен с обычным TLS и с REALITY
без ML-KEM, а на ядре, требующем ML-KEM, подключается только иногда.
Форк 26.10.13 умеет требовать ML-KEM, как оригинальное ядро: переключатель
«Требовать ML-KEM» в меню DPI (`realitySettings.requireMlkem`).
`randomized` и `randomizednoalpn` из меню убраны: рукопожатие срывалось через
раз даже с обычным TLS. `ios`, `edge` и `qq` — снимки браузеров 2020–2022 годов
без постквантовой доли ключа; новый сервер REALITY такое приветствие отвергает,
и со стороны бота это не исправить: им подходит форк без «Требовать ML-KEM».
[Требование REALITY](https://github.com/XTLS/REALITY/commit/8cdf7bf9c7f09cb9814bf08c3eb877f68b85fba8),
[настройка mihomo](https://wiki.metacubex.one/en/config/proxies/tls/).

Сайт-маска (fake domain) для Xray 26.10.17 должен отвечать с ALPN (`h2` или
`http/1.1`), как отвечают обычные сайты и nginx самого бота в режиме «свой
домен». Сервер REALITY 26.10.17 подтверждает SNI в блоке EncryptedExtensions
и подгоняет этот блок под длину блока маски; у маски без ALPN блок пуст, и
сервер отвергает всех клиентов (в журнале с `show` — `padding: -4`).
Ядра 26.10.10 и старше и форк 26.10.13 так не делают; форк 26.10.28 взял
новую библиотеку REALITY и ведёт себя как 26.10.17. Замер 2026-10-19 на
локальной маске: без ALPN 26.10.17 не принимает ни одного клиента, с ALPN —
те же отпечатки, что 26.10.10. Замер 2026-10-29: форк 26.10.28 без ALPN не
принимает никого, с ALPN — те же отпечатки, что форк 26.10.13 (с «Требовать
ML-KEM» — как оригинальное ядро).

Бот проверяет маску сам: из контейнера `xr` (тем же путём, что и REALITY)
при смене fake domain, кнопкой «проверить» в меню Xray и раз в 6 часов из
cron. Меню показывает согласованный ALPN маски либо предупреждение: маска
без ALPN (на ядре 26.10.17+ — «отвергает всех клиентов», на старом — «до
обновления ядра»), без TLS 1.3 или недоступна с сервера. Маска без ALPN, но
с подтверждением SNI ядро устраивает, и бот её не отмечает.

Меню **Xray → VLESS Encryption** включает дополнительное шифрование для
REALITY, WebSocket или XHTTP. Доступны аутентификация X25519/ML-KEM-768
и режимы `native`, `xorpub`, `random`, как в 3x-ui. Ключи создаёт активное ядро
командой `xray vlessenc`; конфиг проверяется до применения. Выключение и
повторное включение сохраняют ключи; для ротации есть отдельная кнопка.
После изменения параметров все клиенты должны обновить подписку.
Серверные ключи не включаются в клиентские профили. При переходе на Trojan
Encryption не применяется; при возврате к VLESS выбранная пара сохраняется.
[Документация VLESS Encryption](https://xtls.github.io/en/config/outbounds/vless.html).

Официальный sing-box 1.14.2 не поддерживает VLESS Encryption и новое
рукопожатие REALITY Xray 26.9.8+. Несовместимая подписка отклоняется с
объяснением; отключение Encryption не исправляет новое рукопожатие REALITY.
Для sing-box нужны прежнее серверное ядро, форк Jolymmiles `v26.10.5`+ либо
WebSocket/TLS или Trojan/gRPC без VLESS Encryption. Форк с этой версии собирает
REALITY из собственного дерева и принимает ClientHello без X25519MLKEM768,
поэтому при выбранном форке подписка sing-box с REALITY выдаётся.
XHTTP также отсутствует в официальном sing-box.
[Формат VLESS sing-box](https://sing-box.sagernet.org/configuration/outbound/vless/),
[его REALITY-клиент](https://github.com/SagerNet/sing-box/blob/v1.14.2/common/tls/reality_client.go).

Основное ядро образа `xr` в `dev` и `master` — XTLS `v26.11.9`;
во втором слоте `v26.10.31` (прежнее основное), в третьем `v26.7.28`, отдельно форк SMUX. Обновите код бота и образ `xr`, затем откройте
**Xray → Ядро / версия**. Меню показывает версии, действительно установленные
в контейнере, и работающий процесс. По умолчанию используется `v26.11.9`
([выпуск upstream](https://github.com/XTLS/Xray-core/releases/tag/v26.11.9)):
отпечаток Chrome 155 по умолчанию, оптимизации XDRIVE для Google Drive,
защита от частных адресов по умолчанию и для MASQUE. Ключ `blockDelay` в
`finalRules` стал устаревшим синонимом `delay`; бот пишет `blockDelay`, потому
что `delay` не знают второй, третий слоты и форк.
`v26.10.29` XTLS отозвал 2026-10-31: программы на Go 1.24+ по умолчанию слушают
TCP как MPTCP, а уязвимость ядра Linux CVE-2026-98432 через слушающий сокет
IPv4 MPTCP даёт удалённый root. `v26.10.31` выключает MPTCP у входов Xray;
кроме того, все контейнеры бота получают `GODEBUG=multipathtcp=0` (через `.env`,
окружение модулей протоколов и `SetEnv` в `config/sshd_config` для процессов,
которые бот запускает по SSH), поэтому MPTCP выключен и у форка, AdGuard Home,
Caddy и остальных программ на Go. Ядро Linux на сервере всё равно обновите.
`v26.10.10` и `v26.10.17` XTLS отозвал 2026-10-21: в их встроенных корневых
сертификатах (`golang.org/x/crypto/x509roots/fallback`) оказались корни со
скомпрометированными ключами, теги удалены. `v26.10.31` — запасное ядро для
отката с `v26.11.9`. `v26.7.28` — ядро со старым поведением: маска REALITY без
ALPN, XDRIVE в нём нет; встроенных корней нет. Клиентам со старым рукопожатием REALITY (sing-box,
отпечатки ios, edge, qq) — `v26.7.28` или форк без «Требовать ML-KEM»; во встроенных
корнях форка сборка поднимает `x509roots/fallback` до исправленной версии.
Если был выбран второй или третий слот, после обновления он запустит другую версию.
Сохранённый выбор дополнительного ядра или форка продолжает действовать.

Переключение проверяет конфигурацию выбранным бинарником, перезапускает Xray
и прерывает текущие соединения. Если запуск не удался, бот пытается восстановить
прежнее ядро и конфигурацию и сообщает результат. Одновременно работает одно
ядро; остальные занимают только место в образе (две дополнительные версии —
около 73 МиБ без сжатия). Выбор сохраняется при пересоздании контейнера.
После смены обновите клиентские подписки: SMUX доступен только в форке,
а совместимость REALITY зависит от версии. Успешная проверка серверного
конфига не гарантирует поддержку протокола конкретным клиентом.

При транспорте XHTTP и форке `v26.10.5`+ в меню **Xray → SMUX** доступен
переключатель **Mux.Cool (XHTTP)**, по умолчанию выключенный. Форк, в отличие
от XTLS, принимает на XHTTP TCP-сессии Mux.Cool: все потоки клиента идут одной
сессией XHTTP, а сервер подаёт в её простаивающий канал KeepAlive, чтобы прокси
и CDN не обрывали его по таймауту. Блок получают только JSON-профили клиентов
Xray: sing-box и mihomo Mux.Cool не поддерживают, в ссылку `vless://` он не
помещается. При включённом SMUX действует SMUX. XHTTP и сам мультиплексирует
запросы, поэтому настройка полезна, только когда важно число сессий. Бот
проверяет версию форка при включении и выключает настройку при переходе на
XTLS; после отката образа `xr` на более старый форк выключите её вручную.

Меню **Xray → XDRIVE** включает запасной канал через облачное хранилище
(оригинальное ядро `v26.9.30`+ или форк `v26.10.5`+). Сервер и клиент не
соединяются напрямую: обе стороны читают и пишут файлы в общей папке WebDAV
(Яндекс Диск, Nextcloud и другие), Google Drive или сервиса, описанного своим
шаблоном. Сервер не открывает для этого порт, а клиенту нужен доступ только к
хранилищу. Вход обслуживает тех же пользователей, что и основной VLESS, всегда
с шифрованием VLESS на собственных ключах. Клиент — только Xray: бот выдаёт
готовый JSON-профиль, в котором лежит доступ к хранилищу, поэтому канал годится
для себя и близких, а под хранилище нужна отдельная учётная запись без личных
файлов. Профиль клиента включает Mux.Cool: без него Xray 26.10.17+ клиента
XDRIVE не запускает, поэтому профили, выданные до этого обновления бота,
нужно выдать заново. Подробная справка — кнопкой в самом меню.

Хранилище **S3** (Yandex Cloud, Cloudflare R2, MinIO и другие S3-совместимые)
работает с оригинальным ядром `v26.10.29`+, форк его пока не знает; клиентам
тоже нужен Xray 26.10.29+. Задаются адрес S3, бакет, регион подписи,
path-style (по умолчанию включён), папка-префикс, ключ доступа и секретный
ключ — ключ лучше выпустить с правами только на этот бакет: он попадает в
профили клиентов. «Проверить хранилище» подписывает запросы AWS SigV4 так же,
как ядро. Тест `tests/xdrive_core_test.php` гоняет трафик через локальную
заглушку S3 (`tests/integration/fixtures/xdrive/s3_server.py`), которая
проверяет подпись.

Версии задаются в `.env` (для локальной сборки — в `override.env`):
`XRAY_VERSION=v26.11.9`, `XRAY_VERSION_2=v26.10.31`,
`XRAY_VERSION_3=v26.7.28`, `XRAY_FORK_VERSION=v26.11.10-1249`.
Слоты хранят место, а не версию: выбранный слот после обновления образа `xr`
запускает ту версию, что теперь в нём лежит. В этом выпуске основной слот —
`v26.11.9` вместо `v26.10.31`, второй — `v26.10.31` вместо `v26.9.30`;
третий и форк не менялись.
Проверьте выбор в меню.
Это параметры **сборки**: после изменения пересоберите `xr`;
`docker compose pull` не меняет состав готового образа. Пустые
`XRAY_VERSION_2`/`XRAY_VERSION_3` исключают соответствующий слот из сборки.
Перед удалением активного слота выберите другой: при старте контейнера
отсутствующий бинарник не подменяется другим, а SSH остаётся доступен для
выбора ядра. Для отсутствующего форка сохраняется прежний авторемонт бота:
возврат к основному XTLS и отключение SMUX. Обычный `make start` скачивает
опубликованные образы, поэтому собственную сборку запускайте без `pull`.

Поддержка общая для XTLS и форка Jolymmiles: новое рукопожатие не включается
переключателем в JSON, его реализует само ядро. Бот проверяет версию REALITY
из метаданных бинарника, поэтому будущий выпуск форка с прежней зависимостью
не считается новым REALITY только по дате релиза. Там же он видит замену модуля
копией из дерева форка (`=> ./third_party/reality`): такое ядро не считается
строгим, хотя версия зависимости совпадает с апстримом. Клиентские параметры MLKEM
выдаются для обоих ядер. Обновление форка задаётся отдельно через
`XRAY_FORK_VERSION` в `override.env` с пересборкой `xr`; перед переключением
при включённом Encryption конфиг проверяется выбранным бинарником.

Shadowrocket объявил VLESS Encryption в версии 2.2.79. Это не подтверждает
работу нового рукопожатия REALITY с любым TLS fingerprint. В журнале бета-версий
есть импорт `support-x25519mlkem768` (2.2.90), а в 2.2.93 исправляется описание
совместимости REALITY/отпечатков. Проверка конкретной версии на iOS необходима;
её нельзя заменить успешным тестом mihomo или Xray.
[App Store](https://apps.apple.com/us/app/shadowrocket/id932747118),
[Shadowrocket News: импорт MLKEM](https://t.me/ShadowrocketNews/1575),
[исправление описания отпечатка](https://t.me/ShadowrocketNews/1634).

В карточке клиента Xray и его relay доступны ссылки `import://` для
**Shadowrocket, v2rayNG, sing-box, Streisand, Hiddify, Karing, mihomo, Rabbit Hole и INCY**.
Ссылка открывает установленное приложение и передаёт ему адрес подписки;
приложение или браузер могут запросить подтверждение добавления. Для mihomo
ссылку `clash://` обрабатывает установленный графический клиент с поддержкой
этой схемы. В Hiddify используется команда `hiddify://import/` и подписка
со списком узлов; маршрутизацию приложение настраивает самостоятельно.
При включённом HWID переход из браузера доступен, а проверка устройства
выполняется при загрузке конфигурации приложением. Ограничения совместимости
протоколов сохраняются независимо от способа импорта.

### Журнал подключений пользователя Xray

Карточка пользователя → **📜 лог подключений**:

- **🕒 По времени** (открывается сразу) — дни от новых к старым; внутри дня
  сайты по времени последнего обращения: `21:05–21:13  site ×6  🇺🇸 Владелец`
  (интервал и число обращений за этот день, порт 443 не пишется). Сверху —
  период, число подключений, сайтов и адресов, последняя активность и онлайн.
- **📊 Сайты** — самые частые за 30 дней, первое и последнее обращение.
- **📱 Устройства** — приложения, которые запрашивали подписку: VPN-клиент и
  его версия, ОС и версия, модель (если приложение их присылает, например Happ
  или Hiddify; при открытии страницы подписки в браузере — браузер), время и
  адрес запроса; адреса подключения к VPN со страной и провайдером. Браузер и
  модель внутри VPN-туннеля не видны.
- **🧩 Группировать по сайту** сворачивает поддомены (`scontent-*.cdninstagram.com`).
- **📄 Скачать журнал .txt** — полный журнал в UTF-8 с выровненными колонками:
  приложения, хронология по дням (время до секунды), сайты, адреса.

Длинный журнал листается страницами. История по дням (`connlog_day`, не больше
300 адресов на пользователя в день, 30 дней) и сведения о приложениях
(`sub_client`, 10 последних на пользователя, 30 дней) копятся с обновления бота;
адреса, известные только по прежним итогам, помечены «⏳ до обновления».
Меню **логи** показывает файлы журналов от изменённых недавно, с размером и
временем; 👁 — последние 40 строк в чате, новые сверху.

Устройства HWID и журнал подключений Xray бот хранит в SQLite
(`config/vpnbot.sqlite`, только для root): регистрация устройства — одна короткая
транзакция, а не перезапись общего файла на каждой выдаче подписки. При первом
запуске нового образа прежние `config/hwid.json` и `config/connlog.json`
переносятся один раз; сами файлы не удаляются, и образ без SQLite после отката
продолжит работать с их состоянием на момент переноса. Резервная копия бота
по-прежнему содержит устройства HWID.

Периодические задачи контейнера `service` идут двумя процессами: `cron.php`
(сроки, лимиты, учёт трафика, онлайн — каждые 10 секунд) и дочерний
`cron.php maintenance` (проверки узлов, загрузки, сертификаты, резервные копии).
Медленная сетевая проверка больше не задерживает отключение по сроку или лимиту;
упавший процесс `maintenance` поднимается заново. Изменения пользователей Xray
применяются через API ядра без перезапуска; перезапуск остаётся для переименования
и когда у отключённого пользователя ещё открыты соединения (так они рвутся).
[Импорт sing-box](https://sing-box.sagernet.org/clients/general/),
[Hiddify](https://hiddify.com/app/URL-Scheme/),
[Karing](https://karing.app/cooperation/scheme),
[Rabbit Hole](https://rabbit-hole-1.gitbook.io/rabbit-hole-docs/for-devs/deep-linking).

### MASQUE и расширенная маскировка UDP

**Настройки → Протоколы → MASQUE** включает отдельный контейнер, по умолчанию
выключенный. В разделе MASQUE задайте адрес и SNI либо выберите домен сервера,
обновите SSL. Нужны доступные TCP и UDP на выбранном внешнем порту (24449 по
умолчанию); внутренний порт всегда 24449. HTTP/3 использует UDP, HTTP/2 — TCP;
оба передают TCP и UDP приложений. Режим выбирается в дополнительных настройках,
автоматического перехода с HTTP/3 на HTTP/2 нет.

В карточке пользователя VLESS откройте **Отдельные подключения → MASQUE**,
скачайте JSON и запустите нативный Xray **26.9.30+**:
`xray run -config profile.json`. Прокси SOCKS5 слушает `127.0.0.1:1080`;
системный TUN этим профилем не включается. После изменения настроек скачайте
профиль заново. В общие профили Mihomo/sing-box MASQUE не добавляется.
Срок, отключение, смена секрета и лимит связаны с основной карточкой пользователя.
Расход опрашивается каждые 5 секунд: между проверками возможен перерасход,
а аварийное завершение может потерять последний не записанный интервал.
Отзыв доступа и изменение серверных настроек прерывают сессии MASQUE.

**XMUX** (дополнительные настройки → Клиент Xray, клиенты Xray 26.10.17+ и
форк 26.10.13+; старые клиенты поле пропускают и работают одним туннелем):
`connections` — сколько туннелей CONNECT-IP клиент держит одновременно (1–4),
`reuse` — сколько секунд туннель принимает новые соединения (60–86400, число
или диапазон). Без этих настроек ядро 26.10.17 само держит один туннель и
переоткрывает его раз в 30–50 минут; начатые соединения доживают в старом.
Каждый туннель занимает адрес из пула сервера (`10.14.0.0/21` и `fd14::/118`,
1022 туннеля с IPv4 и IPv6). Пул IPv4 больше: при исчерпании первым кончается
IPv6 — дальше туннели получают только IPv4 (сеть Docker сервера IPv6 и так не
выводит наружу), а после 2045 туннелей новые получают отказ.

Контейнер использует отдельную сборку Xray `v26.11.9` с небольшим патчем:
пакеты к другим клиентам и шлюзу туннеля отбрасываются до прямой пересылки,
которая в upstream обходит маршрутизацию и пользовательские счётчики.
Остальные приватные адреса блокируются правилами. Основной контейнер `xr`
и его четыре бинарника от этой сборки не зависят. Выход WARP требует работающего
WARP и поддерживает только TCP приложений; прямой обход при отказе не включается.
В `.env` закреплены `MASQUE_XRAY_VERSION`, `MASQUE_SOURCE_SHA256` и
`MASQUE_GO_VERSION`. Это параметры сборки: смена версии требует новой контрольной
суммы, совместимости патча и повторных тестов. Обновление готового образа
выполняется вместе с кодом бота и скриптами контроллера.

Фрагментация и шум из меню **Xray → DPI masking** (клиентская сторона) по
умолчанию попадают в профили подписки Xray отдельным выходом freedom с
`fragment`/`noises`: его понимает любой клиент, а Xray 26.10.29+ лишь пишет в
журнал, что форма устарела. Переключатель «Формат в профилях: finalmask»
переносит те же маски в `streamSettings.finalmask` прокси-выхода, без
предупреждения. Это для клиентов на Xray 26.3.27+: на 26.2.x такой профиль не
загрузится, на более старых ядрах маски молча не действуют (проверено на
выпусках 25.12.8–26.10.29), поэтому умолчание не меняется.

**Xray → DPI masking → finalmask → noise** поддерживает тип `exp` и динамический
пресет: `<b hex>`, `<r N-M>`, `<rc N-M>`, `<rd N-M>`, `<t>`, `<c>`, `<n>`.
Это байты, случайные байты/буквы/цифры, время, счётчик и nonce; содержимое
формируется заново при отправке. Разрешено до 8 пакетов по 1400 байт,
задержка 0–1000 мс, reset 1–86400 с. Активный `exp` требует основного Xray
26.9.30+ и блокирует переход на старое ядро до выключения маски. `reset`
отсчитывается от последнего исходящего UDP-пакета к адресу; это интервал
простоя перед повторным шумом, а не периодический таймер. Ошибка
применения запускает восстановление прежних настроек с проверкой результата.
Для MASQUE собственный переключатель и параметры noise находятся в его
дополнительных настройках; клиент и сервер получают согласованные параметры.
Маска действует на внешний UDP HTTP/3; HTTP/2 её не использует. После изменения
скачайте клиентский JSON заново. Дополнительные пакеты увеличивают расход;
успешный тест туннеля не означает гарантированного обхода любого DPI.

### WARP: режим WireGuard или MASQUE

Сервер держит связь с Cloudflare WARP одним из двух способов; переключатель —
кнопка **«режим»** в меню WARP.

- **WireGuard** (по умолчанию) — туннель `wgcf` по UDP. Быстрее, но у части
  хостингов и провайдеров блокируется.
- **MASQUE** — туннель внутри HTTP/3 на порт 443 (или HTTP/2 по TCP 443,
  кнопка «транспорт MASQUE»). Проходит там, где WireGuard до Cloudflare не
  работает; по скорости это запасной путь, а не ускорение. Нужен образ `wg` с
  ядром Xray 26.10.10+ — бот сам проверяет это и откажет на старом контейнере.

Режим меняет только то, чем контейнер `wp` держит туннель. Маршрутизация
(списки **warp** в Xray, «Выход: warp» у протоколов, «ss через warp»), личные
WireGuard-профили WARP у клиентов в шаблонах и защита от утечки не меняются:
все по-прежнему ходят в SOCKS5 контейнера `wp`, а его процессу разрешён выход
только в туннель.

Для MASQUE в Cloudflare регистрируется отдельное устройство (каталог `masque`
в томе `warp`); аккаунт WireGuard остаётся нетронутым, поэтому переключение
туда и обратно не требует обращений к Cloudflare. Перед переходом на MASQUE
бот делает пробное подключение, не останавливая WireGuard: если MASQUE с
сервера недоступен, режим не меняется. Если новый режим не поднялся уже после
переключения, бот возвращает прежний. «set key» действует в обоих режимах.
Если контейнер запущен в режиме MASQUE без устройства, он регистрирует его сам;
после отказа повторяет попытку с растущей паузой (от 2 минут до 6 часов),
чтобы не упереться в лимит регистраций Cloudflare. Переключение режима и
«set key» в боте регистрируют устройство сразу, без паузы.

Регистрацию выполняет `wgcf` (Cloudflare отклоняет клиентов с чужим
TLS-отпечатком), ключ устройства MASQUE привязывает `scripts/warp_masque.sh`.
Поддержка WARP в MASQUE появилась в Xray 26.10.10 и пока новая. Подробности и
разбор неполадок — в справке меню WARP.

## snolc: отдельный экспериментальный сервис

В меню сервисов доступен **snolc · SSH + Noise**, по умолчанию выключенный.
Для него используется отдельный образ `vpnbot-snolc`, контейнер
`snolc-${VER}`, адрес `10.10.0.26` и **TCP 24448**. UDP приложений передаётся
внутри SSH; публиковать UDP 24448 не требуется. SSH сервера на другом порту
не затрагивается. TLS-сертификат и SNI не нужны; выход пока только `direct`.
При штатном управлении выключатель останавливает и удаляет контейнер, сохраняя каталог
`config/protocols/snolc` с ключами, пользователями и учётом трафика.

Сначала задайте адрес и внешний порт в разделе snolc, затем включите сервис.
Пользователи связаны с VLESS: общий выключатель, срок, квота и ротация доступа.
В карточке пользователя → **Отдельные подключения** скачивается ZIP с личным
профилем и нативным клиентом **Linux x86_64/glibc, Python 3.11+**.
После распаковки: `python3 client.py --install --prepare`, затем `python3 client.py`.
Локальный SOCKS5 слушает только `127.0.0.1:1080` и передаёт TCP/UDP.
Обновление ZIP по личному URL выполняется вручную. Mihomo, sing-box и импорт
SSH-профиля в snolcNG этим экспортом не поддерживаются; мобильная версия
не заявлена. Relay может пересылать TCP на этот порт, сохраняя ключи сервера.

При ручном управлении Docker отключите автоматическое управление сервисами
согласно своей схеме установки и запускайте только профиль `snolc`.
Внешний порт меняется в **Настройки → Ports → snolc**. При ручном управлении
Docker перенесите выбранный порт также в `SNOLC_PORT` и правила nftables,
затем пересоздайте только контейнер snolc; внутренний порт всегда 24448.
Обновите клиентский ZIP после смены порта. При `iptables=false` нужны DNAT
в `prerouting`/`output` на `10.10.0.26:24448` и разрешение `forward` для
нужных источников. Сохраняйте существующие ограничения ASN/списков;
правило NAT само по себе доступ не разрешает. Если уже есть общий
masquerade для `10.10.0.0/24`, дополнительный SNAT не нужен.

После ручного запуска или смены проброса подтвердите порт командой
`python3 scripts/protocol_modules.py confirm-port snolc` из каталога установки.
Она проверяет работающий контейнер и публикацию выбранного TCP-порта,
затем разрешает боту выдачу обновлённых профилей; Docker и nftables она
не меняет. При отключённом управляющем worker выключатель в боте закрывает
слушатель ядра; сам контейнер останавливайте вручную.

Модули закреплены на версии 0.0.4; установщик сверяет SHA256 каждого архива
и сохраняет лицензии. Ядро `0.0.4+vpnbot.6` и все модули клиента (SOCKS5,
carrier-ssh, protection-noise, policy-local) собираются из закреплённых
исходников с проверкой SHA256; бинарники выпуска автора не используются.
Исправлены учёт закрытых потоков, освобождение UDP, зависание последнего
UDP-кадра в буфере, нагрузка процессора в простое и обрыв всего туннеля,
когда приложение читает медленнее канала («mux receive limit exceeded»).
Образ сервиса — Alpine: ядро и все серверные модули собираются из тех же
исходников под musl. Клиентский комплект в ZIP собирается отдельно для glibc.
Клиентские бинарные исправления включены в ZIP, доступный после первого
запуска контейнера; Rust и Docker на клиентской машине не требуются.
Клиент проверяет оба ключа сервера. ZIP содержит
секрет доступа, а `desired.json` — корневой секрет сервера: храните их закрыто.
Резервная копия бота сохраняет серверные ключи и расход; для точного переноса
остановите сервис и скопируйте также весь `runtime`. Не удаляйте отдельно
`policy*.redb` или `admin.json`: сервис откажется стартовать при нарушении
целостности состояния. После аварии неиспользованный резерв квоты может
быть списан; это исключает повторную выдачу уже зарезервированных байтов.

Контейнер ограничен 1 CPU, 256 МиБ памяти и 128 процессами; это также
ограничивает пропускную способность. Пределы: 16 серверных сессий,
16 потоков на сессию, 4 сессии и 32 потока на пользователя.
Используйте исправленный клиент из ZIP бота. SSH-баннер отличается от
OpenSSH. Обход конкретного DPI и неотличимость от обычного SSH не обещаются.

## Встроенные шаблоны и адреса Relay

Бот добавляет шаблоны sing-box `15_direct`, `15_dns_google`, `15_relay` и
Mihomo `mihomo_cust_warp` при первом проходе обслуживания или открытии меню
шаблонов. Выберите нужный шаблон в меню либо в карточке пользователя.
Одноимённые пользовательские шаблоны, их правки, удаление и текущий выбор
по умолчанию сохраняются при последующих запусках.

Адреса промежуточных серверов берутся из раздела **Relay**. Метки
`~relay_hosts~`, `~relay_ips~`, `~relay_domains~` раскрываются при выдаче
подписки: первая используется ключом карты hosts, остальные — элементами
списков адресов/доменов либо строк правил Mihomo. Явно заданная запись hosts
имеет приоритет. Если Relay нет, пустые правила удаляются.

IPv4 доменов обновляются в фоне раз в десять минут; выдача подписки DNS не
ждёт. При временном отказе DNS используется последний успешный ответ.
После удаления Relay его адреса исчезают из выдачи сразу. Явные адреса
IPv6 также поддерживаются, включая правила `IP-CIDR6` в Mihomo.

Для XHTTP между NGINX и Xray используется HTTP/2 через `grpc_pass`, а
новые профили Xray и Mihomo получают `stream-up`; прежние `packet-up`
продолжают работать. WebSocket использует `proxy_pass` с HTTP/1.1 и Upgrade.
Такой выбор соответствует [описанию XHTTP](https://github.com/XTLS/Xray-core/discussions/4113)
и [документации WebSocket в NGINX](https://nginx.org/en/docs/http/websocket.html).

## Routes: правила маршрутизации (regexp / keyword / full / domain)

Списки маршрутизации (**routes** в боте) поддерживают xray-совместимые префиксы,
которые единообразно транслируются в конфиги всех движков — **xray, sing-box,
mihomo/clash** — и работают в том числе для маршрута через **warp**.

Префиксы можно использовать в списках:
- **proxy (domains)** — завернуть в прокси;
- **block** — заблокировать (blackhole / REJECT);
- **warp** — направить через WARP.

### Как вводить

После нажатия **add** отправьте список записей. Разделитель — **перевод строки
или запятая**. Записи с `regexp:` пишите **каждую с новой строки**: регулярное
выражение может само содержать запятые (например `a{1,3}`), поэтому по запятой
такая строка не разбивается.

```
regexp:.*\.ru$
regexp:^([\w\-\.]+\.)xn--p1ai$
keyword:reddit
full:example.com
domain:пример.рф
google.com
```

Или в одну строку через запятую (без regexp):
```
keyword:gigabyte, keyword:reddit, domain:vk.com, 1.2.3.4/24
```

### Префиксы

| Префикс         | Что делает                          | Пример                     |
|-----------------|-------------------------------------|----------------------------|
| `regexp:`       | регулярное выражение                | `regexp:.*\.ru$`           |
| `keyword:`      | совпадение по подстроке             | `keyword:reddit`           |
| `full:`         | точное совпадение домена            | `full:example.com`         |
| `domain:`       | домен и все его поддомены            | `domain:vk.com`            |
| *(без префикса)*| суффикс на sing-box/mihomo, **подстрока на xray** (см. ниже) | `google.com` |
| *(IPv4[/cidr])* | IP-адрес / подсеть                  | `1.2.3.4`, `10.0.0.0/24`   |
| *(IPv6[/cidr])* | IPv6-адрес / подсеть                | `2001:db8::1`, `2001:db8::/32` |
| `ext:`          | категория доменов из внешнего xray `.dat` (**block/warp и маршруты узлов, сервер**) | `ext:dlc.dat:github` |
| `extip:`        | категория IP из внешнего xray `.dat` (**block/warp и маршруты узлов, сервер**)       | `extip:zkeenip.dat:akamai` |
| `geosite:`      | категория доменов из штатной geodata xray | `geosite:category-ads-all` |
| `geoip:`        | категория IP из штатной geodata xray      | `geoip:cn`                 |

У `ext:`/`extip:` **категория обязательна**: `ext:dlc.dat` без `:категория`
xray не разбирает и не стартует, поэтому такие записи вырезаются из серверного
конфига (в списке они остаются, но ни на что не влияют).

`geosite:`/`geoip:` понимает только xray — в правила sing-box и mihomo они не
попадают (у тех своя geodata и свой синтаксис).

Записи с **пустым значением** (`keyword:`, `regexp:` и т.п.) и **некорректные
IP** (`999.1.1.1`, `1.2.3.4/64`, префикс вне 0–32 для IPv4 и 0–128 для IPv6) в
конфиги не попадают и при вводе не сохраняются. Пустой `keyword:` особенно
опасен: в поле `domain[]` у xray голая строка означает совпадение по подстроке,
а пустая подстрока входит в любой домен — весь список превращался бы в
«блокировать всё».

Домены (кроме `regexp:`/`keyword:`/`ext:`/`extip:`) автоматически приводятся к
punycode (`domain:пример.рф` → `domain:xn--e1afmkfd.xn--p1ai`).

### Во что транслируется

| Ввод          | xray `domain[]` | sing-box         | mihomo/clash       |
|---------------|-----------------|------------------|--------------------|
| `regexp:X`    | `regexp:X`      | `domain_regex`   | `DOMAIN-REGEX,X`   |
| `keyword:X`   | `X` *(подстрока)* | `domain_keyword` | `DOMAIN-KEYWORD,X` |
| `full:X`      | `full:X`        | `domain`         | `DOMAIN,X`         |
| `domain:X`    | `domain:X`      | `domain_suffix`  | `DOMAIN-SUFFIX,X`  |
| голый домен   | `X`             | `domain_suffix`  | `DOMAIN-SUFFIX,X`  |
| IPv4[/cidr]   | поле `ip`       | `ip_cidr`        | `IP-CIDR,X/32`     |
| IPv6[/cidr]   | поле `ip`       | `ip_cidr`        | `IP-CIDR6,X/128`   |
| `ext:file:tag`   | `ext:file:tag` в `domain[]` | *(вырезается)* | *(вырезается)* |
| `extip:file:tag` | `ext:file:tag` в `ip[]`     | *(вырезается)* | *(вырезается)* |
| `geosite:X`      | `geosite:X` в `domain[]`    | *(вырезается)* | *(вырезается)* |
| `geoip:X`        | `geoip:X` в `ip[]`          | *(вырезается)* | *(вырезается)* |

> У xray нет отдельного префикса `keyword:` — голая строка в поле `domain`
> уже означает совпадение по подстроке, поэтому `keyword:X` отдаётся как `X`.

### Меню AdGuard

- **⚙️ настройки** — меняются на ходу через API AdGuardHome, без перезапуска и
  разрыва DNS: защита (вкл/выкл, пауза на 10 или 60 минут), безопасный поиск,
  лимит запросов (выкл, 20, 100, 300, 500, 700, 900, 1100 в секунду), режим
  апстримов, срок хранения журнала запросов и статистики (выкл, 1, 7, 30, 90
  дней), скрытие IP клиентов в журнале.
- Лимит запросов AdGuardHome считает на подсеть /24. Все клиенты WireGuard —
  одна подсеть, как и те, кто приходит через контейнеры: заводские 20 в секунду
  делятся на всех, и при большом числе пользователей запросы теряются.
- **📊 статистика** — запросов и заблокировано за период, самые частые домены
  и клиенты (идентификатор из адреса DoH заменяется именем пользователя).
- Апстрим перед добавлением проверяет сам AdGuardHome; неотвечающий не
  добавляется. Апстрим для отдельных доменов: `[/домен/]адрес`.
- ClientID — строчные латинские буквы, цифры и дефис, до 63 символов; пароль
  панели — от 8 до 72 байт. Список разрешённых, если он ведётся, сам пополняется
  новыми пользователями и освобождается от удалённых.
- Настройки клиентов, сделанные в панели, и клиенты, заведённые вручную,
  сохраняются при добавлении, удалении и переименовании пользователей.
- Сброс настроек требует подтверждения. При опубликованном порте DoT и пустом
  списке разрешённых меню предупреждает, что резолвер открыт всем.
- Список разрешённых в меню показывается целиком; у идентификаторов
  пользователей рядом стоит имя.
- **📖 Справка** — в главном меню, настройках и статистике: панель и пароль,
  DoH/DoT и ClientID, список разрешённых, настройки, журнал, апстримы,
  проверка DNS, версия, сброс и неполадки.

### Внешние xray `.dat` (меню routes → dat)

Xray-ядро умеет матчить домены/IP по внешним `.dat` файлам (формат
`geosite.dat`/`geoip.dat`) через токены `ext:file:tag` (домены) и `ext:file:tag`
в поле `ip` (IP). Бот сам качает `.dat` по URL на сервер и подставляет ссылки в
серверные правила `block`/`warp`.

- **routes → dat** — реестр источников. Формат записи: `name.dat:URL`, напр.
  `dlc.dat:https://github.com/v2fly/domain-list-community/releases/latest/download/dlc.dat`.
  Несколько — по одному на строку. Кнопка **🔄 обновить** перекачивает все `.dat`.
  В **⏱ автообновление** выбирается расписание: выкл., готовые интервалы от 30
  минут до 30 дней или **свой интервал** (`90m`, `36h`, `10d`; от 15 минут до 90
  дней). Для интервала от суток можно задать час запуска по часовому поясу бота.
  Меню показывает дату и время последнего успешного обновления и следующего
  запуска, а по каждому файлу — размер, дату загрузки и причину последнего
  отказа. Планировщик использует условный запрос (ETag / Last-Modified): если
  источник отвечает `304 Not Modified`, файл не качается вовсе. xray
  перезапускается только когда содержимое `.dat` реально изменилось. Встроенные
  базы для `geosite:`/`geoip:` обновляются по тому же расписанию.
- При отказе автообновления бот сообщает администраторам (один раз на серию
  отказов) и повторяет попытку через час, а не через полный интервал.
- Файл заменяется только после проверок: ответ должен быть в формате
  geosite/geoip (страница ошибки или обрезанная передача отклоняются), а если
  источник публикует рядом `<ссылка>.sha256sum` (v2fly, Loyalsoldier), сумма
  сверяется — в меню такой файл помечен `sha256 ✅`. Тело пишется сразу на диск,
  поэтому большие базы не упираются в лимит памяти PHP.
- **📂 категории** — список категорий каждого скачанного файла с поиском. Запись
  block/WARP с категорией, которой в файле нет, не принимается, причина
  называется в ответе.
- В списках **block**/**warp** и маршрутах узлов ссылайтесь на категории: `ext:dlc.dat:github`
  (домены) или `extip:zkeenip.dat:akamai` (IP).
- Работает **только на сервере** (block/warp и маршруты узлов применяются серверным ядром Xray).
  В клиентские подписки (xray/sing-box/mihomo) `ext:`/`extip:` не попадают — у
  клиента этих `.dat` нет; для клиента используйте `geosite:`/`geoip:` вручную в
  шаблоне. `includelist`(domains)/`subnetlist` префиксы `.dat` не поддерживают.

**Настройка сервера — не требуется.** Бот кладёт `.dat` в общий каталог
`/logs/geodata` (виден контейнеру `xr`) и сам задаёт ядру `XRAY_LOCATION_ASSET=/logs/geodata`
при каждом старте xray (`restartXray` и `scripts/start_xray.sh`). Правки
`override.env`/пересоздание контейнера не нужны. Guard дополнительно не пишет ссылку
`ext:`/`extip:` в серверный конфиг, пока сам `.dat` не скачан, — ядро не падает.

### `full:` — полный (точный) домен

`full:X` матчит **только сам домен X целиком**, без поддоменов. Нужен, когда
правило должно сработать ровно для одного хоста.

```
full:example.com
```
- ✅ `example.com`
- ❌ `www.example.com` — это поддомен, не совпадает
- ❌ `example.com.evil.net`

Транслируется: xray `full:example.com` · sing-box `domain` · mihomo `DOMAIN`.

### `domain:` и голый домен — домен-суффикс

`domain:X` матчит **сам домен и все его поддомены** — на всех трёх движках
одинаково.

```
domain:vk.com
```
- ✅ `vk.com`, ✅ `m.vk.com`, ✅ `sun9-1.userapi.vk.com`
- ❌ `notvk.com`, ❌ `vk.com.evil.net`

Голый домен без префикса (`google.com`) тоже даёт суффикс на sing-box и mihomo,
**но на xray он трактуется как подстрока** (legacy-поведение: `google.com`
совпадёт и с `google.com.cn`, и с `mygoogle.com`). Поэтому для предсказуемого
суффиксного совпадения на всех движках используйте явный префикс `domain:`.

| Ввод           | xray                | sing-box / mihomo      |
|----------------|---------------------|------------------------|
| `domain:vk.com`| суффикс (`domain:`) | суффикс (`DOMAIN-SUFFIX`) |
| `vk.com`       | **подстрока**       | суффикс (`DOMAIN-SUFFIX`) |

Транслируется: xray `domain:X` · sing-box `domain_suffix` · mihomo `DOMAIN-SUFFIX`.

### `regexp:` — обратный слэш (важно)

В регулярных выражениях ставьте **одинарный** обратный слэш: `\.`, `\w`, `\-`.
Движок — RE2 (Go), общий для xray, sing-box и mihomo.

```
regexp:.*\.ru$
regexp:^([\w\-\.]+\.)ru$
```

⚠️ Если копируете regexp из **JSON-файла**, там слэш экранирован дважды
(`"regexp:.*\\.ru$"` в JSON = один `\` в реальной строке). Вводить в бота нужно с
**одинарным** слэшем (`regexp:.*\.ru$`). Паттерн с двойным слэшем (`.*\\.ru$`) в
RE2 требует литеральный бэкслэш и не совпадёт ни с одним доменом. Бот
автоматически схлопывает случайный двойной `\\` в одинарный `\` (в доменных
именах бэкслэшей не бывает), но канонично вводить с одинарным.

### Пример: домены зоны RU через один список

```
regexp:.*\.ru$
regexp:.*\.by$
regexp:.*\.su$
regexp:.*\.xn--p1ai$
regexp:^([\w\-\.]+\.)ru$
regexp:^([\w\-\.]+\.)xn--p1ai$
regexp:^([\w\-\.]+\.)moscow$
keyword:gigabyte
keyword:ventusky
keyword:qbittorrent
keyword:reddit
```

## Выборочный выход через IPv6

Узлы, группы с выбором живого участника, подписки узлов и применение правил
без перезапуска описаны в [руководстве по узлам выхода](docs/EXIT_NODES_RU.md).

В **Xray → Узлы выхода → IPv6 этого сервера** можно направить выбранных
пользователей и назначения через IPv6 того же сервера. Поддерживаются те же
домены, `domain:`, `full:`, `keyword:`, `regexp:`, `geosite:`, `geoip:`,
`ext:`, `extip:`, IPv4/IPv6 CIDR и наборы `.srs` / `.mrs`, что у удалённой
ноды. Наборы преобразуются в домены и подсети; произвольная логика sing-box
(порты, процессы, вложенные логические условия) этим импортом не переносится.

Локальный выход всегда **только IPv6**: нет AAAA, недоступен IPv6 или передан
IPv4-адрес — соединение закрывается. IPv4 CIDR выбирает маршрут, но не
преобразует адрес в IPv6. Если приложение передаёт IP, для доменных правил
нужен sniffing с заменой назначения (`routeOnly: false`). Распознать домен
удаётся не для каждого протокола. Порядок правил сохраняется: защита и
блокировки выше узла. QUIC для локального IPv6 изначально разрешён; при
проблемах распознавания домена его можно блокировать в карточке узла.

Для выхода с **другого IPv4-сервера** создайте на IPv6-сервере «Профиль для
узла» и выберите в нём **«Выход: только IPv6»**. Добавьте его защищённую ссылку
на исходном сервере, назначьте маршруты и пользователей, переключите
**«При отказе: блок»**. Так IPv4 используется между серверами, IPv6 — от
конечного сервера до назначения. Для старых нод по умолчанию остаётся
**«При отказе: напрямую»**; включая первые секунды после рестарта, пока
проверка не подтвердила доступность ноды. Строгий режим вместо этого блокирует
соединение. Служебный профиль не пересылает трафик в другие ноды.

Если включённому строгому узлу не хватает набора `.srs/.mrs`, нужного `.dat`
или запись маршрута повреждена, бот временно блокирует весь трафик назначенных
ему пользователей: без полного списка нельзя определить безопасный обход.
После восстановления правил блокировка снимается при пересборке конфигурации.
Неудачное обновление при сохранённом рабочем кэше не блокирует пользователей.
Повреждённая ссылка строгой удалённой ноды блокирует её выбранные назначения.
Обычные ноды с прямым запасным выходом сохраняют прежнее поведение.

Чтобы такая блокировка не возникала из-за ошибки ввода, строгий узел не
принимает записи, которые нельзя собрать: набор, который не скачался или пуст,
`geosite:`/`geoip:`/`ext:` без нужного `.dat` и неверную запись. Для
`geosite:`/`geoip:` и `ext:` из реестра routes → dat бот сначала скачивает
`.dat`. Непринятые записи перечисляются в ответе; включить строгий режим, узел,
запись или набор нельзя, пока они не готовы. Если строгий узел не отвечает,
уведомление администраторам и «Куда пойдёт домен» сообщают о блокировке, а не
о прямом выходе. Служебный профиль «Выход: только IPv6» без подготовленной
сети блокирует свой трафик целиком, и его карточка об этом предупреждает.

Удалённым сервером может быть и **3x-ui**: добавьте в бот защищённую ссылку
отдельного клиента VLESS/REALITY (`type=tcp`), VLESS/TLS+WS/XHTTP либо
Trojan/TLS+gRPC. Бот подключается к входу Xray; доступ к API панели не нужен.
На стороне 3x-ui выделите этому подключению отдельный inbound и направьте
его через `inboundTag` в отдельный `freedom` с `sendThrough`, равным IPv6
того сервера, и `ForceIPv6`. Для строгой защиты нужны также конечные запреты
IPv4, внутренних и специальных IPv6-адресов и адресов самого сервера:
одна стратегия DNS не запрещает обращения к IP напрямую. Используйте ядро,
для которого эта защита проверена реальными TCP/UDP-пробами, включая DNS
rebinding; успешная проверка синтаксиса не доказывает поддержку `finalRules`.
На исходном боте остаются домены, CIDR и `.srs/.mrs`, а также «При отказе:
блок». Учётка общего назначения без IPv6-политики на 3x-ui этого не обеспечивает.
Для хостового Xray не нужны Docker-сеть и SNAT из следующей инструкции;
его IPv6 должен быть доступен в сетевом пространстве самого процесса.

Подготовка конечного сервера (однократно, администратором):

1. Добавьте локальный IPv6-выход в боте, пока не назначая пользователей.
   Это заранее закрепляет обычный выход за IPv4. Нужна актуальная защищённая
   сборка Xray из проекта; бот проверяет конфигурацию перед перезапуском.
2. До назначения публичного IPv6 обеспечьте загрузку закрытых IPv6-цепочек
   firewall, в том числе при старте ОС. Настройте выделенный провайдером
   IPv6, маршрут по умолчанию и
   `net.ipv6.conf.all.forwarding=1`. Если маршрут получаете через RA, нужен
   `accept_ra=2` на WAN и доверенный link-local маршрутизатор в firewall.
   Не угадывайте gateway; при `ipv6.disable=1` сначала требуется настройка
   загрузки ОС и перезагрузка по отдельному плану обслуживания.
3. Примените адаптированный nftables-профиль своего сервера. IPv6 `input` и
   `forward` закрыты по умолчанию; разрешены NDP, необходимые ICMPv6-ошибки и
   исходящие соединения единственного контейнера `fd42:7662:6::9` через
   `br-vpnbot6`. Map `ip6 filter egress6_snat` должна сопоставлять этот ULA
   с вашим публичным IPv6. Пустая map закрывает новые соединения. Входящие
   SSH/VPN/DNS/панели по IPv6 не открываются. Как и для IPv4-профилей проекта,
   Docker использует `iptables=false`, `ip6tables=false`,
   `userland-proxy=false`; не смешивайте этот профиль с другим firewall.
4. Из корня проекта выполните:

   ```sh
   python3 scripts/ipv6_egress.py prepare --public <IPv6-сервера> --interface <WAN>
   python3 scripts/protocol_modules.py compose up -d --no-deps --force-recreate xr
   ```

   Подготовка проверяет адрес, маршрут, forwarding, закрытые цепочки,
   SNAT map и защиту обычного выхода Xray. Она не меняет настройки ядра и
   firewall. Дополнительная сеть подключается **только к xr**; Docker не
   маскирует её самостоятельно, исходящий адрес выбирает nftables.
   MTU этой сети — 1280: Linux не пересылает ошибки PTB с link-local
   источником через NAT66. Обычные ICMPv6-ошибки остаются разрешены.
5. Повторите проверку узла в боте, затем назначьте маршруты и пользователей.
   Проверка требует фактический IPv6, совпадающий с настроенным публичным
   адресом. Страну YouTube показывает ответ YouTube; регион стороннего GeoIP
   не заменяет эту проверку. IPv6 не гарантирует конкретную страну или
   отсутствие рекламы.

`config/ipv6-egress.json` — локальная настройка хоста, она не включается
автоматически при переносе пользовательского бэкапа на другой сервер.
Сеть подключается к `xr` по самому наличию файла. Повреждённый файл не
останавливает запуск сервисов: сеть остаётся, обычный выход Xray по-прежнему
закреплён за IPv4, а карточка IPv6-узла просит повторить подготовку.
Перенесённые IPv6-маршруты без подготовленной сети закрываются. Старые
установки без этой настройки дополнительную сеть не получают.

Чтобы отказаться от IPv6, сначала явно переключите/выключите соответствующие
маршруты и служебные профили, затем удалите `config/ipv6-egress.json` и
пересоздайте `xr` той же командой. Закрытые IPv6-правила firewall можно оставить.
Обычный выход остаётся IPv4. При изменении публичного адреса обновите SNAT,
повторите подготовку и пересоберите маршруты кнопкой бота.

## Веб-панель: управление ботом без Telegram

Если Telegram недоступен (заблокированы исходящие к `api.telegram.org` либо нет
самого клиента), тем же ботом можно управлять из браузера. Панель не копия меню,
а тот же самый код: клик по кнопке превращается в такой же `update`, какой
прислал бы Telegram, и уходит в `Bot::input()`, а ответы перехватывает
`app/panel/PanelTransport.php` вместо curl'а наружу. Меню, диалоги «введите
значение», QR, файлы конфигов и редактор шаблонов работают один в один.

Панель поднимается на **отдельном слушателе unit (порт 8090)**, проброшенном
только на `127.0.0.1` сервера: снаружи её нет, на публичном 443 путь `/panel…`
отвечает так же, как любой несуществующий адрес. Заходить — через SSH-туннель.

```shell
# на сервере: адрес панели и, при первом запуске, сгенерированный пароль
docker compose exec php php panel.php url
docker compose exec php php panel.php passwd          # сменить пароль
docker compose exec php php panel.php admin <tg-id>   # если $c['admin'] пуст

# на своей машине
ssh -L 8090:127.0.0.1:8090 <сервер>
# затем открыть http://127.0.0.1:8090/panel<hash>/
```

Первый в списке `$c['admin']` — владелец бота: им становится тот, кто первым
написал ничейному боту, либо id из `panel.php admin` на пустом списке. Добавлять
и удалять администраторов может только владелец и только в Telegram: остальные
администраторы этих кнопок не видят, а в панели состав не меняется вовсе —
общий пароль не подтверждает, кто именно вошёл. Сам себя владелец не удаляет;
сменить владельца — поменять порядок id в `app/config.php` на сервере.

Пароль хранится хешем в `pac.json`; его смена разом сбрасывает все открытые
сессии панели — кроме той, из которой пароль сменили кнопкой в настройках.
Действия в панели бот выполняет по очереди, как сообщения Telegram: если
предыдущая команда идёт дольше 30 секунд, панель попросит повторить. Файлы —
до 20 МиБ. Лента, вложения и загруженные файлы лежат в `/config/panel/`.
В настройках кнопка «Посмотреть пароль панели» показывает пароль под спойлером:
нажмите на скрытый текст, чтобы раскрыть его. Для этого в `/config/panel/`
хранится зашифрованная копия (права `0600`), а ключ к ней выводится из токена
бота в `app/config.php`: каталог панели или резервная копия без `config.php`
пароль не раскрывают. После смены токена, у старой установки, где остался только
хеш, и после восстановления копии на другого бота просмотр появится снова после
успешного входа в панель с текущим паролем либо его смены. Прежний файл ключа
`password-display.key` удаляется при первом просмотре или входе, стартовый
`initial_password.txt` — после первого входа. Сам хеш восстановить в пароль нельзя.

Кнопка «выход» отзывает сессию и на сервере: скопированная кука после выхода
не действует.

Публикации порта на `127.0.0.1` мало: слушатель unit виден всей внутренней сети
`10.10.0.0/24`, а freedom-outbound xray её разрешает (иначе не работает WARP), —
то есть до `10.10.0.7:8090` дотягивался бы любой VPN-клиент, а `<hash>` в адресе
панели есть в каждой ссылке подписки. Поэтому панель дополнительно проверяет,
откуда пришёл запрос: пускает только loopback и шлюз docker-сети (с него
приходит и проброшенный порт, и обращение с самого сервера). Проверка стоит на
**весь слушатель**, а не только на `/panel<hash>`: всё остальное на этом порту
обслуживает тот же `index.php` (подписки, `t=changelog`, `/webapp<hash>/*`,
вебхук `/tlgrm`), и на 8090 они шли бы мимо nginx. Если ходить нужно откуда-то
ещё — перечислите адреса или сети в `.env`:

```shell
PANEL_TRUSTED=                     # напр. 10.10.0.0/24 или 192.168.1.5
PANEL_HOSTS=                       # имя в Host, если заходите не по IP
```

### Если заблокированы только исходящие к Telegram

Полноценный бот в Telegram возвращается одним из способов:

- **ретранслятор Telegram Bot API** на другом вашем сервере, откуда
  `api.telegram.org` открывается (раздел ниже). Настраивается в боте или
  командой `make tgapi`;
- прокси для запросов к Bot API — переменная `TELEGRAM_PROXY` в `.env`;
- своё зеркало Bot API — переменная `TELEGRAM_API` в `.env`.

```shell
TELEGRAM_API=api.telegram.org      # или домен[:порт][/путь] своего зеркала/ретранслятора
TELEGRAM_PROXY=socks5h://wp:1080   # прокси; wp — WARP из этого же compose
```

`TELEGRAM_API` принимает только https-адрес без логина, `?` и `#`.
Значение `http://…` установщик отвергает, а бот вместо него использует
`api.telegram.org`: в путь каждого запроса подставляется токен бота.

## Ретранслятор Telegram Bot API

Бот отправляет ответы, файлы и резервные копии через Telegram Bot API
(`api.telegram.org`). Если с сервера бота этот адрес не открывается (блокировка
у хостера или провайдера, плохой маршрут), бот получает команды, но не может
ответить. Ретранслятор — это nginx уже установленного бота на **другом**
вашем сервере, откуда Telegram доступен:

```text
бот (сервер B) ──https──▶ https://домен-A/<префикс>/bot<токен>/<метод> ──https──▶ api.telegram.org
```

Входящие обновления (webhook) по-прежнему приходят от Telegram прямо на домен
бота B. Пользователям в приложениях Telegram ретранслятор не нужен: для них
есть MTProto-прокси (TeleMT). `TELEGRAM_PROXY` работает и вместе с
ретранслятором.

### Включить ретранслятор (сервер A)

Нужен домен с сертификатом Let's Encrypt (Menu → config). Без него
ретранслятор не включается: клиент проверяет сертификат сервера.

1. **Menu → config → 📡 Telegram API → Ретранслятор → + ID бота.** Отправьте
   числовой ID бота-клиента — часть его токена до двоеточия. Бот B показывает
   свой ID на экране «Адрес Bot API этого бота». Секретную часть токена
   отправлять не нужно; если вставить токен целиком, бот возьмёт только ID и
   посоветует заменить токен у @BotFather.
2. При желании **+ IP**: публичный адрес или сеть сервера B. Тогда остальные
   адреса получают 403.
3. Включите ретранслятор и скопируйте адрес `https://домен-A/<префикс>` —
   он показывается только у работающего ретранслятора. Адрес — секрет, как
   пароль.

**Новый адрес** создаёт другой префикс, прежний сразу перестаёт работать.
Удаление последнего ID бота выключает ретранслятор.

### Подключить бота (сервер B)

**Menu → config → 📡 Telegram API → Адрес Bot API этого бота → указать адрес
ретранслятора.** Бот выполняет `getMe` через новый адрес и сохраняет его,
только если ответ пришёл от этого же бота. Иначе прежний адрес остаётся и
бот объясняет причину. Кнопка «вернуть …» переключает на `TELEGRAM_API` из
`.env` или `api.telegram.org`, тоже после проверки.

Если бот уже не может ответить в Telegram, задайте адрес на сервере B:

```sh
cd /root/vpnbot
make tgapi cmd="api-set https://домен-A/<префикс>"
make tgapi cmd=api-check
```

Адрес хранится в `config/telegram_api` (0600) и перекрывает `TELEGRAM_API`
из `.env`. Его подхватывают бот, cron и обработчик обновлений: ход
обновления приходит тем же путём. В резервную копию этот файл не входит,
потому что на новом сервере ретранслятор может не пускать его адрес. После
восстановления на другом сервере задайте адрес заново. Настройки самого
ретранслятора (`tg_relay` в `pac.json`) в копию входят.

### Команды на сервере

От root в каталоге бота (`cd /root/vpnbot`). Без `make`:
`docker compose exec -T php php /app/tgapi.php <команда>`.

| Команда | Действие |
| --- | --- |
| `make tgapi cmd=status` | Адрес Bot API этого бота и состояние ретранслятора; путь ретранслятора скрыт |
| `make tgapi cmd=api-check` | Проверить `getMe` через текущий адрес |
| `make tgapi cmd="api-set https://домен/префикс"` | Ходить через ретранслятор (сохраняется после успешной проверки) |
| `make tgapi cmd=api-reset` | Вернуть `TELEGRAM_API` из `.env` или `api.telegram.org` после проверки; `cmd="api-reset --force"` — без проверки |
| `make tgapi cmd=relay-on` / `relay-off` | Включить или выключить ретранслятор |
| `make tgapi cmd="relay-bot-add 123456789"` / `relay-bot-del` | Разрешить или убрать бота по ID |
| `make tgapi cmd="relay-ip-add 203.0.113.5"` / `relay-ip-del` | Пускать только с этих адресов или сетей CIDR; пустой список — любые адреса |
| `make tgapi cmd=relay-rotate` | Новый секретный адрес |
| `make tgapi cmd=relay-url` | Показать полный адрес ретранслятора (секрет) |
| `make tgapi cmd=help` | Список команд |

Код выхода: 0 — успех, 1 — отказ (причина в выводе), 2 — неверная команда.

### Как защищён ретранслятор

Ретранслятор видит токены и сообщения ботов, которые через него ходят.
Используйте только свой сервер и не передавайте адрес посторонним.

- Префикс пути — 128 случайных бит, не связан с хэшем бота из ссылок подписок.
- Пропускаются только разрешённые ID ботов и только пути Bot API
  (`/bot<id>:<токен>/<метод>` и `/file/bot<id>:<токен>/<файл>`). Остальное
  под префиксом получает 404, Telegram при этом не запрашивается. Неверный
  префикс неотличим от любого несуществующего адреса сайта.
- Сертификат `api.telegram.org` проверяется (`proxy_ssl_verify on`, имя
  `api.telegram.org`, системный набор CA образа). Подмена DNS или перехват
  канала между ретранслятором и Telegram дают 502, токены не уходят.
- Только `GET` и `POST`, тело до 52 МБ (лимит загрузки Bot API — 50 МБ).
  Запросы, которые уходят в Telegram, ограничены: не больше 30 в секунду
  (всплеск до 90) и 32 соединений с одного адреса, сверх лимита — 429.
  Отказ 404 отдаётся раньше лимита и в Telegram не уходит.
- Необязательный список адресов клиентов (`allow`/`deny`).
- Имя `api.telegram.org` резолвится при запросе (DNS Docker): если DNS
  недоступен при старте, nginx всё равно запускается.
- Все значения, которые попадают в конфигурацию nginx (префикс, ID,
  адреса), проверяются строгими шаблонами. Изменение применяется через
  `nginx -t` и `reload`; при отказе остаются прежние файл и настройка.

**Журналы.** Запросы ретранслятора пишутся в `/logs/nginx_tgrelay_access`
без пути и параметров: адрес клиента, время, метод HTTP, код ответа, код
Telegram, размер и время ответа. `error_log` для ретранслятора выключен:
nginx записал бы туда строку запроса вместе с токеном. Клиент с устаревшим
адресом (ретранслятор выключен, префикс сменён, опечатка) тоже не попадёт в
журналы с путём. Как только у ретранслятора появился префикс, во всех
server-блоках nginx пути вида `…/bot<id>:<токен>…` отвечают 404 и пишутся в
тот же журнал без пути. Если ретранслятор ни разу не включали, `nginx.conf`
не меняется. Журнал виден в меню логов бота и очищается вместе с остальными.

Если адрес ретранслятора или токен утёк: «новый адрес» на ретрансляторе и
новый токен у @BotFather (`/revoke`).

### Что означают ответы

| Код у клиента | Причина |
| --- | --- |
| ответ Telegram (`"ok":true`, `401`, `400` в JSON) | Ретранслятор работает |
| 404 (страница nginx) | Неверный префикс, ID бота не разрешён или путь не Bot API |
| 403 | Адреса клиента нет в списке или метод не `GET`/`POST` |
| 413 | Тело запроса больше 52 МБ |
| 429 | Превышен лимит запросов или соединений |
| 502 | Сертификат `api.telegram.org` не прошёл проверку (перехват канала) |
| 504 | Ретранслятор не достучался до `api.telegram.org` |

## Сертификаты при закрытом порте 80 (acme-window)
При штатной установке/обновлении бот автоматически настраивает хостовую защиту
происхождения контейнеров, а затем окно SSL при наличии совместимых правил
`acme_http_fwd` в основном firewall. Адреса и WAN определяются на сервере;
существующие настройки сохраняются. Подготовка нового сервера, диагностика и
параметры: [Хостовые службы](docs/HOST_SERVICES_RU.md).

Если firewall хоста пускает на порт 80 только свои сети, Let's Encrypt не
проверит домен, и «renew SSL» не сработает. Для такого сервера есть служба хоста
`scripts/acme_window.py`: раз в час она проверяет срок сертификата и, когда
осталась треть, открывает порт 80 элементом набора nftables не дольше чем на
10 минут, принудительно выпускает сертификат кодом бота
(`app/acme_renew.php`) и закрывает порт. Неудачные попытки повторяются через
1, 2, 4 и затем каждые 6 часов (за неделю до истечения — каждый час); выпусков
не больше 3 за 7 дней, неудачных проверок домена — не больше 3 в час. Окно
закрывается и при сбое: время жизни элемента в ядре, `ExecStopPost`, отдельная
служба `OnFailure=` и очистка при следующем запуске. Без службы всё работает как
раньше; в боте её поведение описывает «Настройки → 🔐 SSL автообновление → 📖 Справка».

**1. Что нужно заранее**
- бот с этой функцией (контейнер `php` видит `/acme/request` и `/acme/state`:
  `docker inspect` контейнера php, раздел Mounts);
- на хосте `systemd`, `python3`, `openssl`, `docker`, `nft` и firewall с таблицами
  `ip filter` (цепочка `forward`) и `ip dockernat` (DNAT порта 80 на nginx бота);
- все имена сертификата (домен, поддомены, алиасы) указывают на этот сервер —
  иначе служба не откроет порт и сообщит «имя в DNS указывает не на этот сервер».

**2. Правила nftables** — пустые наборы и постоянные правила, которые на них
ссылаются; пока набор пуст, правила ничего не открывают. В `/etc/nftables.conf`:
```
table ip filter {
    set acme_http_fwd {               # элементы «адрес . порт» добавляет только служба
        type ipv4_addr . inet_service
        flags timeout
        size 8
    }
    chain forward {
        # … защита от спуфинга, лимиты источников, чёрный список — выше …
        iifname "eth0" ct status dnat meta mark != $BLACKLIST ct original ip daddr $PUBLIC_IP ct original proto-dst 80 ip daddr . tcp dport @acme_http_fwd limit rate 10/second log prefix "FWD-CERT-ACME: " level info
        iifname "eth0" ct status dnat meta mark != $BLACKLIST ct original ip daddr $PUBLIC_IP ct original proto-dst 80 ip daddr . tcp dport @acme_http_fwd counter accept comment "acme-window"
        # … разрешения для своих сетей и итоговый отказ — ниже …
    }
}
```
`eth0` — внешний интерфейс, `$PUBLIC_IP` — адрес сервера, `$BLACKLIST` — метка
чёрного списка (без чёрного списка условие `meta mark` убрать). Место правил
важно: после защиты от спуфинга, лимитов и чёрного списка, но до отказа чужим.
Только если порт 80 должен вести к **другому** проекту на том же сервере (цель с
`"redirect": true`), добавьте в `table ip dockernat` набор и правило **перед**
обычным DNAT порта 80 — в цепочках `prerouting` и `output`:
```
    set acme_http_redirect { type inet_service; flags timeout; size 4; }
    # в prerouting и output, перед «tcp dport 80 dnat to <nginx бота>:80»:
    ip daddr $PUBLIC_IP tcp dport @acme_http_redirect counter dnat to 10.10.2.5:80 comment "acme-window-redirect"
```
Проверить файл — `nft -c -f /etc/nftables.conf`. На работающем сервере добавьте
наборы и правила одной транзакцией `nft -f <файл-добавлений>` с командами
`add set` / `insert rule … position <handle>`; расположение и handle существующих
правил показывает `nft -a list ruleset`. Те же изменения сохраните в постоянном
конфиге. Не загружайте целиком файл с `flush ruleset`, если Docker управляет
своими правилами: это удалит и его NAT/фильтрацию. Полная загрузка допустима,
только если конфиг хоста сам восстанавливает все нужные правила контейнеров.
Записи журнала `FWD-CERT-ACME:` показывают, кто ходил в окно.

**3. Настройки службы** — `/etc/acme-window/config.json`, владелец root;
рекомендуемые права — 600. Служба откажет при другом владельце или разрешённой
записи для группы/остальных (чтение, например при 644, допускается):
```json
{
  "public_ip": "203.0.113.10",
  "bot_dir": "/root/vpnbot",
  "targets": [
    {"name": "vpnbot", "kind": "vpnbot", "upstream": "10.10.0.2:80"}
  ]
}
```
| Поле | Значение |
|---|---|
| `public_ip` | адрес сервера: на него должны указывать имена сертификата; по нему же проверяется, какой сертификат отдаёт сервер |
| `bot_dir` | каталог бота, по умолчанию `/root/vpnbot` |
| `name` | имя цели: латиница в нижнем регистре и цифры, до 32 знаков (`vpnbot`, `videobot`) |
| `kind` | `vpnbot` — сертификат этого бота; `nginx-ssl` — соседний контейнер с certbot и скриптом `/renew-certificate.sh` |
| `upstream` | адрес и порт 80 контейнера, куда ведёт DNAT (у бота — nginx, `10.10.0.2:80`); служба сверяет его с контейнером |
| `verify_port` | порт, на котором проверяется отдаваемый сертификат (по умолчанию 443) |
| `redirect` | `true` — на время окна порт 80 ведёт к этой цели (нужен набор `acme_http_redirect`); только для одной цели |
| `container`, `cert_file` | для `nginx-ssl`: имя контейнера и путь на хосте к его `fullchain.pem` |
| `auto` | автообновление при первом запуске (по умолчанию `true`; потом переключается в боте) |
| `label` | подпись в боте: `{"ru": "…", "en": "…"}` |

**4. Установка и проверка** (из каталога бота, от root):
```shell
python3 scripts/setup_acme.py ensure --bot-dir "$PWD" --wait-lock 30
acme-window renew vpnbot --dry-run           # пробный выпуск у staging Let's Encrypt, сертификат не меняется
acme-window status                           # срок, следующая попытка, последний итог
nft list set ip filter acme_http_fwd         # снова пустой — порт закрыт
```
Установщик кладёт `/usr/local/sbin/acme-window`, юниты `acme-window.service`
(запуск), `acme-window-close.service` (закрытие при сбое), `acme-window.timer`
(раз в час со случайной задержкой до 20 минут) и `acme-window.path` (запросы
бота — сразу) в `/etc/systemd/system/`, каталоги `acme/request` и `acme/state`
в каталоге бота. Состояние службы — `/var/lib/acme-window/state.json`, журнал —
`journalctl -u acme-window -u acme-window-close`.

**5. Обслуживание**
- Служба копируется в `/usr/local/sbin/acme-window` и проверяется при штатном
  обновлении бота. Для ручного обновления используйте `python3 scripts/setup_acme.py ensure`;
  настройки и состояние сохраняются, актуальная установка не прерывает выпуск.
- Ручные команды: `acme-window renew <цель>` (выпустить сейчас, с учётом лимитов),
  `acme-window check` (наборы и правила на месте), `acme-window close-all`.
- Удаление: `sh scripts/install_acme_window.sh --uninstall` — юниты и программа
  удаляются, окно закрывается; `/etc/acme-window` и `/var/lib/acme-window`
  остаются. Правила с пустыми наборами можно не убирать: они ничего не открывают.
- В бэкап бота входят сертификат и признак Let's Encrypt; настройки и состояние
  службы остаются на сервере.

**6. Если не работает**
- `FATAL: нет /etc/acme-window/config.json` или `владелец должен быть root…` —
  шаг 3; `FATAL: в nftables нет наборов или правил окна` — шаг 2.
- `fail_dns` — имя сертификата не указывает на `public_ip`; `fail_preflight` —
  нет контейнера nginx/php или он не на адресе `upstream`; `fail_issue` — ответ
  Let's Encrypt в `journalctl -u acme-window`; `rate_limited` — исчерпан лимит.
- Если служба не отвечает больше трёх часов, бот показывает это в меню и
  «renew SSL» снова запускает certbot сам (при закрытом порте 80 — без успеха).

После установки в **Настройки** появляется «🔐 SSL автообновление»: срок,
последняя попытка, включение автообновления и выпуск сейчас. «renew SSL» тогда
передаёт запрос службе, а не запускает certbot сам.

## Сборка, проверка и выпуск

GitHub Actions собирает полный комплект при push в `dev`/`master`, ручном
запуске и по расписанию — 1-го и 15-го числа в 04:00 UTC. Плановая и ручная сборки обновляют
базовые слои и пакеты без Docker-кэша; закреплённые версии протоколов, PHP и ветка
Alpine сами на новую major/minor-версию не переключаются. Расписание GitHub
исполняется из основной ветки репозитория: workflow только в `dev` ещё не
заменяет расписание основной ветки.

Все прямые загрузки исходников, клиентов и инструментов полного прогона
используют общий загрузчик: до шести попыток на каждом канале с паузами
и ограничением времени. После отказа исходного URL запрос повторяется
через Cloudflare DNS-over-HTTPS; для GitHub releases дополнительно доступен
API того же официального релиза. Системный DNS не меняется, проверка TLS
остаётся обязательной. Git, Cargo, npm и загрузки модулей Go также допускают
до шести сетевых попыток; Go сохраняет резерв получения модулей напрямую.
После загрузки обязательна проверка закреплённой SHA-256: несовпадение суммы,
ошибки тестов и проверки безопасности по-прежнему останавливают выпуск.

Собственные Alpine-образы используют стабильную ветку 3.24, включая
WireGuard/WARP, OpenConnect, OpenVPN и IPsec: подмена репозиториев на `edge`
удалена. AmneziaWG собирается закреплённым Go в отдельном этапе; компилятор
не входит в рабочий образ. Версии OpenVPN, ocserv, strongSwan и pppd при смене
базы сохраняются. CI отдельно проверяет фактическую версию Alpine и репозитории
этих четырёх образов. AdGuard сохраняет поддерживаемую базу официального
образа Alpine 3.23; TrustTunnel использует Alpine 3.24.
Их системные пакеты также обновляются при сборке и проходят общий допуск.

1. Все 18 образов получают отдельные теги кандидата. Манифест связывает
   commit, запуск CI и неизменяемые digest каждого образа.
2. CI проверяет PHP 8.4/8.5, версии бинарников и известные уязвимости пакетов
   ОС и обнаруживаемых библиотек. Исправимые HIGH/CRITICAL, устаревшая база
   сканера или неполный комплект останавливают публикацию.
3. Одноразовая Ubuntu VM в GitHub создаёт полную установку с нуля: 25 сервисов,
   тестовых пользователей и отдельные VPN-клиенты. Проверяются реальный трафик,
   ограничения доступа к внутренним службам, циклы выключения/включения,
   backup/restore с повторным трафиком, отказы, откат PHP/NGINX на предыдущий
   опубликованный комплект и Bot API. Отдельный VPS не нужен. Ошибка или пропуск
   обязательной проверки блокирует выпуск; автоматического перехода на
   сокращённые проверки нет. Этот workflow не исполняет код PR.
   Для первого выпуска `master`, когда `bundle-latest` ещё отсутствует, откат
   проверяется на уже допущенном комплекте `bundle-dev`.
4. Только после всех успешных проверок те же образы, без повторной сборки,
   объединяются в выпуск. Одной операцией меняется указатель `bundle-dev`
   или `bundle-latest`; расписание публикует только `bundle-nightly`.
   Старые индивидуальные теги образов не используются для смешанного обновления.

Обновление через бот сначала получает проверенный манифест, соответствующий
ему код и необходимые образы. Ошибка скачивания или нехватка места на этом
этапе отменяет обновление до остановки служб. Явные пины `sha-*`, собственные
образы в Compose и несовместимые локальные коммиты требуют ручного решения.
Рабочий манифест хранится в `update/image-bundle.json`, предыдущий — рядом
в `image-bundle.previous.json`. Перезапуск и повторное включение протокола
используют digest активного комплекта; для уже скачанных образов registry
при перезапуске не требуется.
Штатная очистка сохраняет образы активного и подготовленного комплектов,
включая образы выключенных протоколов. Образы предыдущего комплекта удаляются
(около 2 ГБ диска); его манифест остаётся, и для ручного отката образы
скачиваются из реестра по digest. Загрузка манифеста и очистка согласованы
блокировкой; при повреждении манифеста удаление образов не выполняется.

Автоматического развёртывания на рабочих серверах нет. Перед первым переходом
со старой схемы дождитесь успешной публикации комплекта для нужной ветки.
Комплект содержит 18 образов, включая snolc. Обновляющий скрипт выпусков
без snolc (с 2026-10-06) ждёт ровно 17 образов и безопасно отклоняет такой
комплект до остановки служб. Переход идёт через промежуточный выпуск, который
принимает образ snolc: сначала обновитесь до него, затем ещё раз — до выпуска
со snolc. Комплект без snolc допускается только как предыдущий, для отката.
Откат требует согласованных старого кода и манифеста и проверки совместимости
формата данных; один лишь старый Docker-тег недостаточен. Сохранение предыдущего
манифеста не заменяет резервную копию. При ошибке восстановления runtime-данных
обновляющий скрипт оставляет службы остановленными и сохраняет снимок для
восстановления, а не запускает пустые настройки.

Все задания выполняются на серверах GitHub: для публичного репозитория минуты
GitHub Actions не ограничены, собственный тестовый сервер не нужен. Ручной
запуск из браузера — вкладка **Actions**:

| Что нужно | Workflow → **Run workflow**, ветка | Флажки |
|---|---|---|
| только тесты (без сборки и публикации) | `tests`, `dev` | — |
| полный прогон: тесты, сборка, CVE, стенд, публикация комплекта `dev` | `images`, `dev` | — |
| то же с автослиянием в `master` | `images`, `dev` | `promote_master` |
| пересобрать `master` заново | `images`, `master` | `full_build` |

Флажок `home_runner` отправляет задания на собственный runner с меткой
`vpnbot-home`, только если в репозитории задана переменная
`VPNBOT_HOME_RUNNER=enabled`; без неё задания всегда идут на серверы GitHub.

Для своей копии репозитория: автослияние в `master` использует секрет
`PROMOTE_TOKEN` (fine-grained токен на этот репозиторий с правами Contents,
Workflows и Actions на чтение и запись), необязательный `NVD_API_KEY` ускоряет
проверку компонентов. Пакеты `ghcr.io/<владелец>/vpnbot-*` после первой
публикации сделайте публичными — тогда серверы скачивают образы без входа в
реестр.

Полный прогон по умолчанию строгий. В ручном `images` доступны отдельные
необязательные допуски (все выключены по умолчанию):

- `allow_waivers` — только точные, ещё не истёкшие исключения из
  `scripts/ci_vuln_waivers.json`; другие уязвимости продолжают блокировать выпуск.
- `allow_test_failures` — завершённые с ошибкой функциональные тесты интерфейса
  (полнота переводов, язык надписей, отображение версий)
  из явного списка `FUNCTIONAL_TESTS` в `scripts/ci_release_policy.py` становятся
  предупреждениями. Все тесты всё равно выполняются. Новые и неизвестные тесты,
  Python, протокольные стенды, LAN/ACL, установка, резервное копирование,
  откат, ошибки инфраструктуры и тайм-ауты остаются обязательными.
- `allow_vulnerabilities` — известные блокирующие CVE/GHSA из проверки компонентов
  и Trivy становятся предупреждениями. Сканирование выполняется полностью;
  секреты в образах/слоях, неподдерживаемая ОС, неполные отчёты и отказ сканера
  по-прежнему блокируют выпуск. Патчи безопасности из сборки не удаляются.

Сборка контейнеров, контроль SHA и полный состав комплекта обязательны при
любых флажках. Допущенные ошибки перечисляются в журнале и сводке Actions,
а безопасные идентификаторы сохраняются в `admission.json` внутри транспортного
образа комплекта. Автоперенос передаёт те же разрешения прогону `master` и
публикует ровно проверенный комплект. Комплект с предупреждениями нельзя
перенести в строгом режиме; истёкшее исключение также отклоняется.

Комплект образов публикуется только после сборки, проверок CVE и сетевого
стенда. Два правила избавляют от повторной работы, не ослабляя этого условия.
Комплект собирается из образов одного запуска и одного коммита, но не обязательно
одной попытки: после сбоя достаточно перезапустить упавшие задания, остальные
образы не пересобираются. А `master`, перемотанный ровно на коммит, комплект
которого уже допущен в `dev`, получает те же самые образы без пересборки и
повторного стенда (задание `promote`); для любого другого коммита идёт полный
прогон. Флажок `full_build` при ручном запуске требует полного прогона и в этом
случае, а запуск по расписанию всегда собирает образы заново.

Стенд получает только исходники и образы. Рабочие конфиги, ключи, учётные записи
Telegram/WARP, архивы и данные установок не используются. Одноразовые ключи и
сертификаты создаются внутри VM; Telegram API заменён локальным HTTPS-сервисом,
WARP проверяется через отдельный WireGuard-peer без регистрации у провайдера.
Служебный GitHub-токен используется для checkout и загрузки образов, не передаётся
тестовым контейнерам. Перед их запуском выполняется выход из registry; `.git`
checkout не монтируется в установку. Внешние порты стенда привязаны к loopback.
Перед запуском CI проверяет все профили Compose: посторонние каталоги хоста,
внешние тома, переменные с токенами и публичные привязки портов запрещены.

Сырые журналы, профили, ключи и бэкапы не загружаются в артефакты и кэш; они
удаляются при завершении; GitHub также удаляет временную VM. В артефакты CI попадают только
идентификаторы образов и допуск, связанный с комплектом и исходниками тестов.
VM не заменяет проверки на физических клиентах iOS/Android, в сети провайдера
и длительные испытания под нагрузкой. После изменения входных данных или неудачного запуска
используйте **Re-run all jobs**, чтобы не смешивать результаты разных сборок.
